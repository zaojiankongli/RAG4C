## 1. 实战测试基线（可复现）

**压测环境**：`scripts/bench/mock_upstream.py`（固定 ~100ms 延迟模拟上游）+ 真实 Milvus
（192.168.100.128:19530）+ catalog schema **head (0036)** + 98 文档语料。
并发 32 / 总量 96 / `--warmup 4`。

| 负载 | 成功率 | QPS | P50 | P95 | 含义 |
|---|---|---|---|---|---|
| distinct | 100% | **69.2** | 440ms | 520ms | 全 miss 缓存，真实吞吐 |
| hotspot | 100% | **78.4** | 391ms | 454ms | 缓存击穿合并路径 |
| mixed | 100% | **66.6** | 395ms | 735ms | 八成热点两成长尾 |

**对比**：完整链路修复前（catalog schema 落后 → 全部弃权）测得 QPS 3.97-4.7 / P50 6.7-7.8s
——弃权路径因 catalog 连接失败开销反而更慢。修复后完整链路快一个数量级。

## 2. 实战测试暴露并修复的 5 类 MySQL 8.4 兼容缺陷

| # | 缺陷 | 位置 | 修复 |
|---|---|---|---|
| 1 | `CURRENT_TIMESTAMP` 无精度（MySQL 8.4 报 1067） | 迁移 99 处 | → `CURRENT_TIMESTAMP(6)` |
| 2 | `server_default="CURRENT_TIMESTAMP"` 字符串被 SQLAlchemy 加引号 | orm.py 46 处 | → `text("CURRENT_TIMESTAMP(6)")` |
| 3 | TEXT 列设默认值（8.4 报 1101） | 0017 description | → nullable=True 无默认值 |
| 4 | `trigger` 保留字作列名（8.4 报 1064） | 迁移 6 处 | → `quoted_name("trigger", True)` + CHECK 反引号 |
| 5 | `information_schema.TRIGGERS.TABLE_NAME` 列名变更（8.4 报 1054） | catalog_schema.py | → `EVENT_OBJECT_TABLE` |

另补：3 个开发租户 owner（0016 前置校验）；数据库从半迁移混乱状态**完整重建到 head（0036）**
并回灌 98 文档等数据（`scripts/backup_catalog_data.py` / `restore_catalog_data.py`）。

**遗留待修**：`_head_schema_issues` 对 CHECK 约束的读取在 MySQL 8.4 下误判
（约束真实存在 412 个，但被报 missing/invalid）——影响 schema 完整性校验的准确性，不阻塞运行。

## 3. 已知性能瓶颈（来自 performance.md §4 实测 + 本次压测）

1. **裁判阶段 `verify_l3` 占端到端延迟 45%~50%**（实测 17.8s / 30.9s，真实 LLM 场景）——
   用与生成同一个大模型、prompt ~6900 token。**非缓存能解决**（缓存空间已基本用尽）。
2. **检索增强功能配了但没接线**：`hyde_on`/`subqueries_on`/`stepback_on` 默认关；
   `retrieval/auto_filter.py` 的 `create_auto_filter` **零调用方**（死代码）。
3. 嵌入/改写/路由 LLM/裁判**仍无熔断**（检索/生成/重排已覆盖）。
4. 第二轮检索（`rag.py:417-422`）收益近乎为零。
5. 指标/熔断状态仍是单进程内存态（挡住横向扩容）。

## 4. 业界参考（GitHub/论文）

- **两阶段 groundedness gate**（[rag-knows-wrong](https://github.com/aamishrafique/rag-knows-wrong)）：
  确定性引用覆盖检查 + 可选 LLM 裁判——与 RAG4C 的 L1/L2（确定性）+ L3（LLM）分层一致，
  印证"先确定性后 LLM"的降级策略正确。
- **本地裁判蒸馏**（[groundcheck](https://github.com/enached134-ctrl/groundcheck)）：用
  QLoRA 蒸馏的本地裁判替代高价裁判——对应 RAG4C judge 槽位换更快模型的优化方向。
- **分层基准化**（[production-rag-lab](https://github.com/tkarim45/production-rag-lab)）：
  每层独立 benchmark——RAG4C 已有 `scripts/bench/`，方向一致。
- **生产级 RAG 参考**（[Production-grade-RAG](https://github.com/AdilShamim8/Production-grade-RAG)）：
  结构化日志/错误处理/健康检查——RAG4C 已具备。

## 5. 升级计划（含验收标准）

> 按"收益/风险"排序。每项独立闭环：计划→执行→验收→反馈。

### P1. 修复 `_head_schema_issues` 的 MySQL 8.4 CHECK 约束误判（高价值，中风险）
- **内容**：约束读取逻辑适配 MySQL 8.4（`information_schema.CHECK_CONSTRAINTS` 结构变化）。
- **验收**：`_head_schema_issues` 返回空（不再误报 412 个约束缺失）；
  `migrate_catalog.py status` 显示 `current`；相关测试全绿。

### P2. 裁判阶段延迟优化（最高价值，中风险）
- **内容**：按 performance.md 建议的三个方向选一：
  a) judge 槽位换更快模型（纯配置，零代码）；
  b) L3 裁判抽样/异步化（答案先出，判定后补）；
  c) 裁判与生成并行。
- **验收**：真实 LLM 场景下单查询端到端延迟下降 ≥ 20%（对照 performance.md 的
  17.8s/30.9s 基线）；答案质量不降（评测指标持平或更好）。

### P3. 检索增强功能接线（中价值，低风险）
- **内容**：`auto_filter` 接入检索管线（`retrieval/pipeline.py` 加参数），消除死代码；
  评估 hyde/subqueries/stepback 开关的默认值。
- **验收**：`auto_filter` 有真实调用方；开关打开时检索管线正确走增强路径；
  相关测试覆盖新接线。

### P4. 补齐 LLM 类组件熔断（中价值，中风险）
- **内容**：嵌入/改写/路由 LLM/裁判加熔断（复用现有 CircuitBreaker 模式）。
- **验收**：模拟下游故障时，这些组件快速降级（不耗尽超时×重试）；
  熔断状态在 `/api/health` 可见；测试覆盖。

### P5. 完整链路性能回归门禁（高价值，低风险）
- **内容**：把本次的完整链路压测固化为回归门禁脚本（`scripts/bench/run_full_gate.sh`），
  设定 QPS/P95 阈值（如 distinct ≥ 50 QPS、P95 ≤ 800ms），纳入 CI。
- **验收**：门禁脚本可一键复现；阈值内通过；性能退化时门禁变红。

### P6.（可选）指标/熔断跨副本（低优先，高成本）
- 单进程内存态 → Redis 共享。收益在横向扩容场景，单副本无感。登记为后续。

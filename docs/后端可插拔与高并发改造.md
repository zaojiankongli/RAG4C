# RAG4C 后端可插拔与高并发改造

> 审查与改造日期：2026-08-17  
> 范围：模型 Provider、查询与 SSE、缓存、健康探测、文档入库、Catalog 事务、Pipeline 生命周期与解析器降级

## 1. 审查结论

本轮改造后，后端的可插拔边界和单进程并发控制已形成闭环：Embedding、Reranker、LLM 使用统一的线程安全 Provider 注册表；查询、SSE 和入库任务进入有界执行器；查询缓存具备 single-flight；健康探测可复用旧快照；Catalog 的文档配额和计数更新改为数据库原子操作。

当前实现适合单进程部署以及经过容量规划的多 worker 部署，但不应把“单进程并发安全”等同于“跨进程全局限流”。缓存、single-flight、信号量、执行器和指标均为进程内状态；部署多个 worker 时，总并发和队列容量会按 worker 数量近似线性放大。

## 2. 可插拔设计改造

### 2.1 统一 Provider 注册表

新增 `core/providers.py`，提供泛型、线程安全的 `ProviderRegistry`：

- `register(name, factory)`：注册或替换 Provider 工厂；
- `unregister(name)`：卸载 Provider；
- `names()`：列出当前可用 Provider；
- `create(name, config)`：按名称创建实例，并对未知名称给出可操作错误。

Embedding、Reranker、LLM 分别拥有独立注册表，避免不同类型 Provider 相互污染：

| 能力 | 注册表 | 内置 Provider |
|---|---|---|
| Embedding | `EMBEDDING_PROVIDERS` | `local`、`api` |
| Reranker | `RERANKER_PROVIDERS` | `local`、`api` |
| LLM | `LLM_PROVIDERS` | `openai`、`openai_compatible` |

原有 `create_embedder`、`create_reranker`、`create_client` 调用签名保留，因此现有装配代码无需迁移。第三方实现可在启动阶段注册工厂，不需要修改核心分支判断。

### 2.2 初始化与线程安全

- Embedding、Reranker、LLM、Milvus 客户端均增加惰性初始化锁，避免并发首请求重复加载模型或重复创建连接；
- 本地 FlagEmbedding/FlagReranker 推理采用保守串行，规避模型实例线程重入问题；
- `rag.py` 的默认 Pipeline 使用双重检查锁，显式传入 settings 时仍创建隔离实例，并提供 `reset_pipeline()`；
- `rag_graph.py` 对编译图缓存加锁，避免高并发下重复编译。

## 3. 高并发改造

### 3.1 查询与 SSE

普通查询和 SSE 共用有界 `ThreadPoolExecutor` 与并发信号量：

- 默认真实执行并发为 4；
- 默认等待队列上限为 20，容量耗尽返回 HTTP 429；
- 排队和执行共用 240 秒 deadline，防止排队后重新获得完整超时窗口；
- HTTP 请求超时不会提前释放真实执行槽。同步 SDK 调用无法安全强杀时，worker 会继续持槽，直到后台调用真正结束；
- 执行器支持惰性创建、lifespan 关闭和关闭后的重新创建。

SSE 不再为每条流创建 daemon thread。生产者使用共享执行器，并通过 `run_coroutine_threadsafe(queue.put)` 向容量为 256 的异步队列写入，从而提供背压；终止事件也不会因 `QueueFull` 被丢弃。

### 3.2 查询缓存与 single-flight

查询缓存仍为 10 分钟 TTL、最多 64 条，但缓存键已扩展为：

```text
tenant_id + query + 排序后的 ACL + retry
```

这避免了租户串读、ACL 顺序造成的重复缓存，以及 retry 语义不一致。相同键并发 miss 时只允许一个请求计算，其余请求等待同一结果，避免缓存击穿。

### 3.3 健康探测

健康探测增加 single-flight：

- 快照未过期时直接返回；
- 快照过期且已有旧值时，由一个请求刷新，其他请求立即读取旧快照；
- 首次启动没有快照时，并发请求最多等待 3 秒。

该策略避免探活高峰同时访问 Milvus 和 LLM 端点。

### 3.4 文档入库

文档入库从“每任务一个裸线程”改为有界 `ThreadPoolExecutor`：

- 默认同时执行 2 个任务；
- 默认排队 8 个任务，队列满返回 HTTP 429；
- 同一文档已有活动任务时返回 HTTP 409；
- Pipeline 按 worker 线程复用，避免每个任务重复初始化模型和连接；
- lifespan 关闭时回收执行器和 Pipeline 持有的 Milvus 连接；
- 执行器关闭后可按需重新创建，支持重复 lifespan 测试和进程内重载。

### 3.5 Catalog 事务与配额

SQLite 启用 WAL、外键约束和 30 秒 busy timeout。tenant/dataset 首次创建改用数据库方言级 upsert，覆盖 SQLite、MySQL/MariaDB 和 PostgreSQL；其他方言使用 savepoint 回退。

`create_document` 现在在同一事务内完成 tenant/dataset 确保、租户归属校验、文档插入和计数更新。`bump_counts` 使用 SQL 原子增量，避免并发读改写丢失更新。文档配额通过条件 `UPDATE` 原子占位，配额不足抛出 `CatalogQuotaError`，HTTP 层转换为 429。

chunk 配额自 2026-08-22 起在**嵌入之前**有了一道闸门（`IngestPipeline._enforce_chunk_quota`，超限抛 `QuotaExceededError`），此前它只是个从无生产调用方的函数；计数仍在入库完成后按实际差量更新。但**超卖问题依旧存在**，而且性质没变：这道闸门是「读一次计数、再决定」，不是原子预留，严格的“预留、确认、失败补偿”协议仍未实现。多个大文档并发入库时 chunk 配额仍可能短暂超卖。这是当前的并发边界，不应在生产验收中忽略。

另有两处缺口：`sources/runner.py` 那条入库路径调完 `add_file` 从不调 `bump_counts`，闸门在这条路径上读到的计数偏低；**文档数**配额至今没有生产调用点，只有 chunk 配额真正生效。

### 3.6 解析器降级

PDF Fast 引擎 `pdf-inspector` 缺失或 classify 异常时，如果 Vision 插件可用，路由会自动降级到 Vision，并记录 `fallback_reason`；没有可用 Vision 引擎时仍抛出可操作错误。可选插件缺失不再阻断整条入库链路。

## 4. 配置与容量

| 环境变量 | 默认值 | 含义 |
|---|---:|---|
| `RAG4C_QUERY_MAX_CONCURRENT` | 4 | 每进程查询真实执行并发 |
| `RAG4C_QUERY_QUEUE_MAX` | 20 | 每进程查询等待队列上限 |
| `RAG4C_QUERY_TIMEOUT_S` | 240 | 查询排队与执行统一 deadline（秒） |
| `RAG4C_QUERY_CACHE_TTL_S` | 600 | 查询缓存 TTL（秒） |
| `RAG4C_QUERY_CACHE_MAX` | 64 | 每进程查询缓存条目上限 |
| `RAG4C_INGEST_MAX_CONCURRENT` | 2 | 每进程入库执行并发 |
| `RAG4C_INGEST_QUEUE_MAX` | 8 | 每进程入库等待队列上限 |

若部署 `W` 个应用 worker，不考虑外部网关限流时，查询执行并发约为 `4W`、查询等待容量约为 `20W`、入库执行并发约为 `2W`。应根据 MySQL、Milvus、Embedding、Reranker 和 LLM 的实测 P95/P99 延迟与限流额度调整，而不是只提高应用侧线程数。

## 6. 生产部署边界与建议

1. 限流、缓存、single-flight、最近查询和指标均为进程内状态。需要全局限流或跨实例去重时，应引入网关与 Redis 等共享协调层。
2. 多 worker 不应共享同一个 Milvus Lite 文件；生产多进程部署应使用 Milvus server。
3. 本地模型推理为保证线程安全而串行。需要提高吞吐时，优先将模型服务化，使用 GPU batching 或多个独立模型进程。
4. 同步 SDK 超时只能停止 HTTP 等待，不能安全终止正在运行的 Python 调用；容量评估应包含慢调用继续占槽的时间。
5. 为 chunk 配额补充预留、确认和失败补偿机制，才能提供严格的高并发配额上限。
6. 上线前使用真实请求分布压测，观察排队时间、拒绝率、P95/P99、下游 429 和连接池占用，再调整并发与队列。
7. MySQL、Milvus、Embedding、Reranker 和 LLM 才是端到端吞吐的主要瓶颈。应用层线程数必须服从下游容量，避免把背压转移为级联超时。

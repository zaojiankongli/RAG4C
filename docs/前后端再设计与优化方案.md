# RAG4C 前后端再设计与优化方案

> 编制：资深 AI Agent 开发视角
> 编制日期：2026-08-31
> 状态：**方案待评审**（按 计划-执行-验收-反馈 循环逐项落地，正反馈继续、负反馈反思）
>
> 本文档回答一个问题：**"如果由我来对这个项目的前后端功能做一次再设计和再优化，我会怎么做、为什么、按什么顺序、如何判定每一步是否成功。"**
> 它不是一次性的重构清单，而是一套**带闭环的执行方法**——每一个优化项都是一个完整的 计划→执行→验收→反馈 循环，
> 验收通过（正反馈）就推进下一项；验收失败或引入回归（负反馈）就停下来反思、修订、重跑，而不是带病前进。

## 0. 结论先行（TL;DR）

基于对仓库的实际勘察（代码、测试、构建产物、既有审查报告），我的判断是：

1. **地基已经比多数同类项目扎实**：三层引用验证、双阈值弃权、RunRegistry、SSE 流式、
   统一错误契约、Milvus 注入防护、热更新、L2 配置/可达分离、熔断器修复……这些是 2026-08 月
   几轮高强度审查与加固的成果（`docs/审查报告与优化计划.md`，667 后端测试 + 228 前端测试全绿）。
   **再设计的前提是"不要破坏这些已被反向验证过的防线"。**
2. **真正的再设计空间不在"加功能"，而在四件事**：
   - **契约层**：前后端类型靠手写（`frontend/src/types/rag.ts` 733 行 vs `models/schemas.py`），
     漂移是必然的——这是全仓风险最高、收益最确定的一项；
   - **单体文件**：`server/app.py` 156KB/3394 行、`config/settings.py` 1408 行、
     `frontend/src/App.tsx` 1064 行、`frontend/src/api/client.ts` 785 行——可维护性瓶颈；
   - **安全面收敛**：当前桥服务大量 API 无认证（依赖 127.0.0.1 本地绑定），
     认证模式只在 Runs API 上做过一次，需要推广并统一；
   - **性能/体积**：前端仍有 900kB chunk 警告；后端遗留"让 Milvus 回传 dense_vector
     做真实余弦"这条已记录在案的欠账。
3. **执行方法**：按优先级分 8 个闭环（§5），每轮严格走 计划→执行→验收→反馈；
   验收标准全部量化（命令、门禁、回归数），负反馈走 5 Whys 反思后重跑（§6）。

### 1.3 契约现状（最值得警惕的一点）

```
Python 侧: models/schemas.py（202 行） + 27 个 API 模块各自定义 Pydantic 模型
TS 侧:     types/rag.ts（733 行手写） + runs.ts + 各 enterprise-* 域内 model.ts
同步方式:  无。全靠"提交时人眼对照"。
```

FastAPI 本身免费提供 OpenAPI schema，而当前没有任何一步 CI 或代码生成消费它。
字段改名、类型收窄、枚举增删，前端不会得到任何编译期信号——直到运行期拿到未知字段。
这是**漂移必然发生**的地方，也是再设计的第一优先级。

## 2. 再设计目标与原则

### 2.1 目标（SMART 化）

| # | 目标 | 可验收口径 |
|---|---|---|
| G1 | 前后端契约单一事实源，消灭手写漂移 | CI 中运行生成器，diff 为空才通过；字段改名后前端编译期即报错 |
| G2 | 后端单体文件瘦身到可维护规模 | `server/app.py` < 800 行（仅装配+lifespan+核心传输），业务进 service 层 |
| G3 | 认证/多租户/审计策略全站统一 | 中间件一层实现，API 声明式标注；Runs API 模式推广到全部管理端点 |
| G4 | 前端可维护性：巨型组件与客户端拆分 | `App.tsx` < 400 行；`client.ts` 拆为 transport + 领域 API；行为不变由 228 测试守护 |
| G5 | 前端体积收敛 | 生产构建无 900kB 警告（echarts/tdesign 按需引入） |
| G6 | 可观测性补齐 | 全 API 结构化访问日志 + 请求 ID 贯通；指标可画出 p50/p95 走势 |
| G7 | 评测体系升级 | EvalReport v2 + baseline/compare + release gate（README 遗留项落地） |
| G8 | 桌面端安全收口 | Tauri CSP 非 null；远程绑定必须配置 token 才能启动 |

### 2.2 原则（不可妥协项）

1. **防线优先**：任何重构不得改变既有安全/降级语义（引用验证、弃权、熔断、fail-closed）。
   改动若触碰这些路径，必须配反向验证（把改动回滚后测试应变红）。
2. **行为等价重构**：G2/G4/G5 类结构性改动以"测试全绿 + 契约不变"为第一验收条件；
   功能增强与结构重构分离，绝不混在一次提交里。
3. **小步闭环**：一个优化项 = 一个闭环 = 一次可回滚的提交。禁止"大爆炸式"重构。
4. **证据驱动**：每个决策写明依据（实测/代码位置/历史报告），不写拍脑袋结论。
5. **正反馈继续、负反馈反思**：验收未过不得进入下一项；反思结果写回本方案的"反思台账"（§7）。

## 3. 后端再设计

### 3.1 分层目标架构

```
现状:  route(server/*_api.py) ──> 业务逻辑散落(app.py / core/*) ──> 基础设施(Milvus/MySQL/Redis/SQLite)
目标:  route(server/*_api.py，纯参数校验+DTO) ──> application service(server/services/*) ──> domain(core/*) ──> infrastructure
```

- **路由层**：只做 校验→调 service→序列化；不持有业务状态。
- **service 层**（新增 `server/services/`）：事务边界、编排、错误映射。从 `app.py` 和
  巨型 `*_api.py` 中下沉。
- **domain 层**（现有 `core/`）：保持纯 Python，不依赖 FastAPI；这是当前已经做得好的部分，**不动**。
- **配置**：`settings.py` 1408 行按段拆分为 `settings/{core,retrieval,generation,verify,eval,server,security}.py`
  组合式 Settings（pydantic-settings 多源），兼容 `RAG4C_` 前缀不变。

**理由**：`app.py` 156KB 的现状意味着任何新端点都在和 3394 行共享一个文件的生命周期；
而 `core/` 已经证明了该团队有写出好模块的能力——问题只在"装配层"没有跟上。

### 3.2 契约单一事实源（G1，最高优先）

- 在 `models/` 建立 **API 契约模型目录**（如 `models/api/`），所有请求/响应 Pydantic 模型集中管理；
  27 个 API 模块只允许引用这些模型。
- 新增脚本 `scripts/gen_frontend_types.py`：读取 FastAPI app 的 `app.openapi()`，
  用 `openapi-typescript` 风格生成 `frontend/src/types/generated/`（含 schema_version 头）。
- 手写 `types/rag.ts` / `runs.ts` 逐步迁移为 generated 的 re-export + 少量领域扩展；
  领域扩展与生成物分文件，禁止改写生成物。
- CI 门禁：`python scripts/gen_frontend_types.py && git diff --exit-code`，有漂移即红。

**理由**：这是全仓"单点投入产出比"最高的一项——一次改造，永久消灭一类跨端 bug。

### 3.3 安全面统一（G3）

现状：Runs API 有 loopback/Bearer/tenant 三层访问控制（`server/run_ops.py`），
其余 API 依赖 127.0.0.1 绑定。一旦部署方把宿主改成 0.0.0.0（docker-compose 已在），
管理端点（文档入库、配置写、评测执行、企业域）就裸奔。

- 把 `run_ops.py` 的鉴权中间件泛化为 `server/security.py`：
  - 所有 `/api/*` 统一经过 身份解析（loopback 免认证 / Bearer / OIDC 已有基础）→ 租户解析（`X-RAG4C-Tenant`）→ 审计日志；
  - 端点声明式标注 `public / operator / tenant-scoped`，默认 `tenant-scoped`（fail-closed）；
  - 对 `knowledge_auth.py`、`enterprise_*` 现有的零散鉴权做收敛，统一到一个请求上下文。
- 配置写接口（`/api/config/update`）与评测执行（`/api/eval/run`）强制要求 operator 级凭证，
  不再以"本地绑定"为唯一防线。

**理由**：安全设计应当是"默认拒绝、显式放行"，而不是"默认放行、依赖网络边界"。
README 已把 loopback 免 token 作为安全边界，本项是把该边界从 Runs API 推广到全站。

### 3.4 可观测性补齐（G6）

- 访问日志中间件升级为结构化（JSON lines，含 query_id、租户、耗时、错误码），保留现有人类可读格式开关。
- `query_id` 贯通：HTTP 头（`X-RAG4C-Query-Id`）→ RunRegistry → SQLite history → 日志，
  前端错误提示直接展示 query_id，支持"拿 ID 去查"。
- 指标补三个：**弃权率、引用失败率、端到端 P95 延迟**（现有 metrics 已有基础，加维度即可）；
  其中弃权率要按 §1.1 的教训区分"真无答案"与"降级所致"（`retrieval_scores_comparable` 标记已具备）。

### 3.5 性能遗留项收口

- 落实审查报告遗留的"让 Milvus 回传 `dense_vector`，本地算真实余弦"，
  解决 rerank 宕机期间检索侧无相关性把关的问题（代价：每查询多 40–80KB 响应体，需实测权衡）。
- 子查询 fan-out 超时已有保险丝；追加"超时即取消在途任务"的治理（审查报告明确说当前只是保险丝）。

### 3.6 评测体系升级（G7）

- EvalReport v2：加入 per-question 明细可导出、弃权/引用失败归因、baseline 快照。
- `baseline / compare / release gate`：评测结果入库（复用 run-history 或独立 eval 表），
  支持"本次 vs 上次"显著性对比；release gate 以固定阈值（如幻觉率、引用失败率上限）阻断劣化。
- 复用现有双裁判（Groundedness / Relevance），不引入第三个裁判。

## 4. 前端再设计

### 4.1 组件与状态结构（G4）

- **App.tsx 拆分**（1064 行 → ~350 行）：
  - `AppLayout.tsx`（Sider/菜单/顶栏/Topbar）；
  - `AppRoutes.tsx`（lazy 路由表 + Suspense 边界 + ErrorBoundary）；
  - `AppTheme.tsx`（主题上下文消费，从 AppProviders 中下沉）；
  - `EnterprisePortal.tsx`（16 个 enterprise-* 域的入口装配，与知识工作台解耦）。
  - 行为等价：228 个既有测试是回归守护。
- **client.ts 拆分**（785 行 → transport + 领域 API）：
  - `api/transport.ts`：fetch 封装、超时/Abort、ApiError、重试、base_url 管理（现有能力原样迁移）；
  - `api/query.ts` / `api/health.ts` / `api/eval.ts` / `api/documents.ts` / `api/runs.ts`：按域分组；
  - 页面只 import 领域 API，不直接碰 transport。
- **状态管理评估**：当前 Context 嵌套 5 层且 App 组件树巨大。先量化（哪些 Context 被多少页面读），
  若存在"深读"（深层组件读远端 Context），拆出 1–2 个 **selector 型 hook**（如 `useWorkspaceScope` 已存在），
  不急于引入外部状态库——TDesign/React 18 的现状下，Context + memo 足够。

### 4.2 性能与体积（G5）

- **ECharts 按需引入**：`echarts/core` + 按页面注册所需图表/组件，替换全量 `import * as echarts`；
  这是当前最大可压缩体积项。
- **TDesign 按需**：确认构建链路支持 tree-shaking（Vite + ESM 应已支持），
  检查是否存在 `tdesign-react/es` 全量路径引用（App.tsx 的 `./ui/index` 迁移应已完成，需核对）。
- **chunk 策略**：恢复 `chunkSizeWarningLimit` 到合理值（如 500kB），
  以"真实无警告"而非"抬阈值"为验收标准（findings 里明确反对抬阈值）。
- 复用既有 `PageState`/`ErrorBoundary`/骨架屏体系，新增页面默认带加载态模板。

### 4.3 契约消费（与后端 G1 联动）

- `types/generated/` 由 OpenAPI 生成；`types/rag.ts` 变为 generated 的薄 re-export。
- 前端新增 `npm run types:gen` 脚本 + `npm run check:contract`（diff 校验）。
- SSE 事件的 `BackendRunEvent` 已是 typed，保持；REST parity（README 遗留项）作为后续闭环。

### 4.4 体验与可访问性

- 统一错误呈现：ApiError.kind（timeout/aborted/http/network）映射到 PageState 模板 + 可复制 query_id。
- 保持已完成的 dark/light、reduced-motion、焦点、skip-link；新增页面默认走同一套 a11y 基线
  （Playwright 截图 + axe 的既有流程继续作为验收手段）。
- 桌面端（Tauri）：配置 CSP（`tauri.conf.json` 从 `null` 改为白名单），
  这是 findings 记录的欠账，安全优先。

## 5. 执行路线：8 个闭环（计划→执行→验收→反馈）

> 依赖关系：C1 先行（契约是其他一切的地基）；C2–C4 相互独立可并行；
> C5 依赖 C4（拆完 client 才好按域优化体积）；C7 依赖 C1 的 generated types。

| 轮次 | 闭环 | 目标 | 主要风险 | 验收标准（正反馈判据） |
|---|---|---|---|---|
| C1 | 契约单一事实源 | G1 | 生成器引入的差异量过大，迁移成本失控 | 生成脚本跑通、CI diff 门禁绿、既有 228 前端测试全绿 |
| C2 | 后端装配层瘦身 + settings 分段 | G2 | 拆分中破坏懒加载/热更新语义 | 667 后端测试全绿 + `tests/test_config_hot_reload.py` 反向验证 + app.py < 800 行 |
| C3 | 安全面统一（鉴权中间件推广） | G3/G8 | 误伤 loopback 本地体验 | 安全回归套件全绿 + 远程绑定未配 token 启动即拒绝（新测试） |
| C4 | 前端巨型文件拆分 | G4 | 行为等价性被破坏 | 228 前端测试全绿 + 关键页 Playwright 截图 diff 无意外变化 |
| C5 | 前端体积收敛 | G5 | echarts 按需引入后某图表缺失 | 生产构建无 900kB 警告 + 所有图表页截图基线对比通过 |
| C6 | 可观测性补齐 | G6 | 结构化日志破坏现有日志消费脚本 | smoke/log 消费脚本全绿 + 新指标断言（弃权率/引用失败率） |
| C7 | 评测体系升级 | G7 | baseline 对比的统计口径争议 | `eval/run_eval` 干跑绿 + compare 报告可生成 + release gate 测试覆盖 |
| C8 | 端到端验证与文档收口 | — | 范围蔓延 | 全量门禁（后端 pytest + 前端 vitest/build + Playwright 基线）一次通过；本方案与 README 更新 |

### 5.1 每个闭环内的标准动作

**计划（Plan）**
- 写明：目标、改动文件清单（预估）、风险与缓解、验收命令、回滚方式（本仓无 git，需人工备份受改文件到 `backups/`）。
- 复跑一次相关既有测试，确认"改动前基线"是绿的。

**执行（Do）**
- 按"行为等价优先"实施；结构改动与功能改动分提交。
- 触碰安全/降级路径时，先写"反向验证用例"（回滚改动后必须变红）。

**验收（Check）**
- 命令门禁：后端 `python scripts/run_tests.py` + `ruff check`；前端 `npm run lint` + `npm test` + `npm run build`。
- 契约门禁（C1 起）：`npm run check:contract` diff 为空。
- 截图基线（涉及 UI 的轮次）：`frontend/output/shots/` 关键页对比。
- 性能断言（涉及性能的轮次）：门禁里跑基准（参照 README Task14 的 percentiles 方式）。

**反馈（Act）**
- **正反馈**：验收全部通过 → 记录结果到 §7 台账 → 进入下一闭环；若该轮有顺带发现，登记为新的后续项。
- **负反馈**：任一验收项失败 → 停止推进 → 走 §6 反思流程 → 修订计划后**重跑同一闭环**，不得带病进入下一项。

## 6. 反馈与反思机制（负反馈处理）

### 6.1 反思流程（5 Whys + 证据）

1. **复现**：用失败命令原样复现，记录精确失败信息（禁止"印象中好像没过"）。
2. **5 Whys**：连续追问为什么失败，直到根因不是"操作失误"而是"设计/假设缺陷"。
   （本仓库 `docs/审查报告与优化计划.md` 里有大量先例：RRF 归一化方案在动手前被推倒、
   `l2_enabled` 语义拆分的反复——这些偏差记录比"一次做对"更有价值。）
3. **修订**：把根因与修订方案写回闭环的计划段（保留原计划原文，就地标注偏差，沿用该仓库的文档惯例）。
4. **重跑**：修订后重新执行同闭环；连续 2 次负反馈仍未过的项，降级为"暂缓"，登记原因，不硬闯。

### 6.2 正反馈的"继续"也必须有纪律

- 正反馈 ≠ 任务完成：记录"这个闭环引入了什么新的可观察行为"（如 fan-out span 重叠、阈值语义变化），
  避免下一个闭环在错误假设上叠加。
- 每完成 3 个闭环做一次**横切回归**（全量门禁 + 截图基线），防止增量累积的隐性退化。

## 8. 已识别的风险与边界

| 风险 | 缓解 |
|---|---|
| 契约生成器引入大量 diff，迁移成本高 | C1 独立成轮，允许分文件灰度迁移（先 runs/query，后 enterprise-*） |
| 鉴权中间件推广误伤本地开发体验 | loopback 免认证语义保留，与 run_ops 完全一致；用中间件单元测试钉死 |
| settings 分段破坏热更新 | C2 验收强制包含 `test_config_hot_reload` 反向验证 |
| echarts 按需引入导致图表空白 | C5 验收含全部图表页截图基线；先用一个页面试点再推广 |
| 本仓库无 git，回滚依赖人工备份 | 每轮开始前备份受改文件到 `backups/<轮次>/`；不依赖"我记得原样" |
| 范围蔓延（做完 8 轮还想做） | 8 轮之外的想法一律进"后续项"清单，不进当前方案 |

**明确不做（本轮边界）**：不改引用验证/弃权/熔断的核心算法语义；不引入新的前端状态库；
不做数据库迁移（MySQL catalog 结构冻结）；不重写 LangGraph 编排（只做 canonical parity 的评估）。

### 1.1 三条"100% 弃权"路径的细节

这三条是本次审查的核心，值得单独说明。**弃权门本身是对的**——对照组
`decide([0.95],[0.9]) -> (False,'')` 正常放行。问题全部出在**喂给它的输入**。

**(a) RRF 分数与阈值差了一个数量级**（`retrieval/pipeline.py:507`）

`item.score` 只在 rerank **成功**分支被覆写成 reranker 相关度（0–1）。四条路径会跳过它：
`rerank_on=False`、熔断器打开、`RerankError`、分数数量不符。这四条都被明确设计为
"优雅降级"，日志写 `rerank 失败，使用原始顺序`。此时残留的是 Milvus RRF 融合分：

```
milvus.rrf_k = 60  →  max RRF = 2/(60+1) = 0.03279
pipeline.retrieval_score_threshold = 0.3
decide([0.03279], None) -> (True, '知识库无相关内容')
```

**dense 和 sparse 双双命中第一名的完美结果，也比阈值低 9 倍。**
reranker 一挂，整个服务静默变成一台什么都答不出来的机器。

> **⚠️ 实施期修正（2026-08-22）：本条的定性一开始就浅了，"归一化"方案是错的。**
>
> 初版计划（和你批准的选项）是"min-max 归一化到 [0,1]"。动手前我按定义推了一遍，
> 结论是它不成立：
>
> ```
> fused(d) = Σ_r 1/(k + rank_r(d))       ← 只吃名次，不吃相似度
> ```
>
> 返回列表的 top-1 **必定**在某一路排第 1，所以它的融合分恒 >= 1/(k+1)，
> 与"这篇到底相不相关"完全无关。实测五种场景（完美命中 / 一般 / 毫不相关）
> 分数全落在 `[0.0164, 0.0328]` 这个窄带里，彼此无法区分。
>
> 于是归一化只是把失效方向翻了个面：top-1 名次恒为 1 → 归一化分恒 >= 1/路数
> （双路 >= 0.5，单路 = 1.0）→ 恒 > 0.3 → **闸门从"全拒"变成"全放"**。
> 把 100% 假弃权换成 100% 假通过，不是修复。
>
> **不是尺度不对，是信号根本不存在**，任何缩放都变不出来。
> 已改为**如实承认不可评估**：`RetrievalResult.reranked` 标记分数落在哪把尺子上，
> rerank 未生效时检索闸门不参与判定（`retrieval_scores_comparable=False`），
> 由蕴含闸继续把关，并在 trace 里明示降级。经你确认后按此实施。
>
> 遗留：rerank 宕机期间检索侧确实没有相关性把关了。根治要让 Milvus 回传
> `dense_vector` 本地算真实余弦（零额外往返，代价是每查询多 40–80KB 响应体），
> 列为后续项。


**(b) 空列表 ≠ None**（`verify/abstention.py:79-81`）

门禁契约里 `None` = "不参与判定"，`[]` = "有证据但无可用蕴含分" → 弃权。
但两个编排器都无条件写 `list(verification.entailment_scores.values())`
（`rag.py:453`、`rag_graph.py:238`），**永远传不出 None**。于是：

- `entailment_mode=skip` 在 `verifier.py:372` 直接 return，dict 原封不动 → `[]` → 弃权。
  这与 `settings.py:919` 文档承诺的"只剩检索分数这一道闸"**完全相反**。
- L3 judge 故障时 `verifier.py:394-401` 给每条声明写 `0.5`，而阈值是 `0.6`
  → `max([0.5,0.5]) < 0.6` → 弃权。**且是在检索和生成都已付费之后**。
  judge 抖动与"知识库里没有"对用户完全不可区分。

```
decide([0.95], [])         -> (True, '证据不足以支撑可靠声明')
decide([0.95], [0.5,0.5])  -> (True, '证据不足以支撑可靠声明')
decide([0.95], [0.9])      -> (False, '')      # 对照组，正常
```

### 1.3 稳定性：熔断器语义是反的

`core/circuit.py:127-142` 的 `_transition` 先写 `self._state = state`，
再 `if prev == state: return`，在到达 `elif state == "closed" and record:
self._failures = 0` 之前就短路返回了。于是 `record_success()` 的清零永不执行，
计数器只增不减：

```
第1轮: 1次失败 + 500次成功 → failures=1
第2轮: 1次失败 + 500次成功 → failures=2
第3轮: 1次失败 + 500次成功 → failures=3
第4轮: 1次失败 + 500次成功 → failures=4
第5次失败（其间累计 2000 次成功）→ 熔断打开，allow()=False
```

一个 0.2% 瞬时错误率的健康上游，运行足够久后**必然把自己熔断**，
且因为计数器不衰减，这是永久性的。

> **已修（2026-08-22）**：清零移到同态短路**之前**。同时修掉一处更隐蔽的
> 半开令牌泄漏：探测额度靠调用方回调归还，若某个探测既没 `record_success`
> 也没 `record_failure` 地消失（吞异常 / 进程被杀 / 用了 `allow()` 却忘记记账），
> 令牌永久泄漏，此后 half_open **比 open 还糟**——open 冷却期满会自愈，
> half_open 会永远拒绝一切且无路可救。现在在途令牌有一个冷却期长度的寿命。
>
> 回归测试 `tests/test_circuit_breaker.py`（13 条）。**我把修复回滚后重跑验证过
> 这些测试确实会红**：4 条失败，正好覆盖这两个缺陷；其余 9 条在新旧实现下都绿
> （其中"半开探测成功后闭合"这条路径旧代码本来就对——`prev=half_open != closed`，
> 那个 elif 会执行，所以清零只在 closed→closed 时丢失）。

### 1.6 生成失败会被报成"成功但答案为空"（阶段 3 发现，2026-08-22）

这条是**我自己在阶段 2 引入的回归**，写流式契约测试时被抓出来的，三个编排器都有。

`rag.py:482` / `rag_graph.py:276` / `rag_stream.py:207` 都写着：

```python
answer=generated.answer if generated is not None else "",
```

这行本身就是自证：作者知道 `generated` 可能是 None，而处理方式是发一个空字符串。
但同一个 `QueryResult` 里 `abstained=False`。于是 LLM 整个挂掉时，用户收到的是一个
**HTTP 200、abstained=False、answer=""** 的响应——看起来成功，实际空白。

从前这条路径被遮蔽着：生成失败 → `entailment_scores` 为空 → 编排器无条件传 `[]`
→ 门读成"证据不足" → 顺手弃权。**弃权是对的，但理由是错的**（说的是"证据不足"，
真相是"根本没生成出来"）。阶段 2 把 `[]` 改成 `None`（L3 没跑就是没跑）之后，
这层偶然的遮蔽消失了，缺陷露了出来。

trace 里其实一直写着 `生成失败（弃权）`——它以为自己弃权了，而结果字段说没有。

**已修**：三处都在验证阶段弃权门之前加 `if generated is None: abstain, reason = True, "生成失败"`。
弃权门问的是"证据够不够"，它回答不了"有没有答案"这个问题，不该指望它兜底。

> 顺带一个方法论上的教训：阶段 2 我只改了"传什么给门"，没有回头问"门原先那个
> 错误的输入，是不是正好挡住了别的什么东西"。移除一层错误的保护时，要先查清楚
> 它当时到底在保护谁。

|---|---|---|

这一阶段的范围里。现在的形状是"用到谁才等谁"：生成全部提前发出，各阶段在
自己原来的位置取回结果，编排一行没动。

**三处与计划的偏差，都值得单独记一笔：**

- **23 最终没有接缓存。** 计划里写的"接入 `embed_query` 的缓存"经不起推敲：
  声明是 LLM 当场生成的，**永远不会重复**，缓存它只会把一堆一次性条目写进
  与别的应用共用的 Redis；chunk 正文倒是会重复，但 `core/embed_cache.py:28-32`
  明确写了正文嵌入不进这个缓存（入库路径会把共用实例撑爆），而逐条走
  `embed_query` 又会把一次批量拆成 N 次串行——比现状更糟。真正的解法是让
  Milvus 把 `dense_vector` 一起返回（这些向量本来就在库里），那是另一条路，
  已记在待办里。
- **两处"合并成一次批量"都引入了同一个新失败模式：切分点错位。** 分开调用时
  少返回几条只是少配几对；合成一批之后少一条，后半段整体前移——路由会静默
  指向错误的分支，声明会被指派到错误的 chunk 而且带着 `status="ok"`。两处都
  加了长度校验并**拒绝缓存半成品**，各配了一条"少返回"的用例。这两条比任何
  性能断言都重要。
- **25 顺带补了一根保险丝。** 原来的 `future.result()` 不带超时：一路卡死的
  `hybrid_search` 会把整条 HTTP 请求永久挂住，而那个请求还占着一个准入名额
  （上限 32），几路下来服务对外就是整体不可用——这是可用性问题，不是性能问题。
  现在整批共用一个截止时刻（`subquery_fanout_timeout_s`，默认 30s），超时后
  带着主检索结果照常返回。**超时不会取消已经发出的检索**，线程仍被占着，
  所以它只是保险丝，不是治本的办法。

**新增两个配置项**（`RAG4C_PIPELINE_SUBQUERY_FANOUT_WORKERS` /
`..._TIMEOUT_S`）。增强器的生成池宽度**刻意没有做成配置**：那不是"多少合适"
的调优问题，而是"这三件事本来就该同时做"的结构问题——多一条线程无处可用，
少一条就有一个增强器要排队等另一个。

**span 语义有一处必须知道的变化。** `hyde` / `subqueries` / `stepback` 三个
span 现在**相互重叠**，把它们相加不再等于这一段的墙钟时间（trace 里会有一行
明说这件事）。每个 span 报的仍是"这一步花了多少工作量"，而不是"主线程在这
里坐了多久"——并发之后主线程可能在某个阶段一秒不等，若按本地墙钟量，同一份
工作量会在两次查询里报出完全不同的数，trace 就没法用来定位慢在哪了。

### 5.1 结论：架构已经一致，差距全在默认值和健壮性

参考实现的链路是
`Question → Entity Extraction → Vector Search → Subgraph Expansion → LLM Rerank → Answer`，
把图结构以 **ID 引用**存在 Milvus 里，让"图遍历"退化为主键查找。

本仓库 `retrieval/graph_retriever.py:89` 的链路是
`实体向量检索 → _expand_relations（沿 relation_ids / entity_ids 做 BFS）→
关系向量检索 → 合并 → LLM 重排 → final_top_k`。

**是同一个算法。** 不需要重写。

有两处本仓库反而更好：

- 参考实现用**邻接矩阵 + 矩阵乘法**算 n 度扩展，是 O(实体×关系) 的稠密矩阵；
  本仓库用迭代式 ID 查找 BFS，不吃这个内存，而且能在**每一跳都下推租户过滤**
  （`_expand_relations` 把 `tenant_id` 传进每次 `get_entities_by_ids`）。
  矩阵法做多租户隔离的代价要高得多。
- 参考实现是三个集合（entity / relation / **passage**）；本仓库是两个，
  passage 通过 `passage_ids` 落回主 chunk 集合。文本只有一份真源，少一处漂移。

### 5.2 差距

当前默认值：

```
expansion_degree              = 1      ← 多跳实际上是关的
entity_similarity_threshold   = 0.9    ← 对 BGE-M3 余弦而言非常高
relation_similarity_threshold = -1.0   ← 关闭（与实体侧不对称）
final_top_k                   = 3
```

**(a) `expansion_degree=1` 抵消了这个特性的全部意义。**
参考实现存在的理由就是找到**查询里根本没提到的桥接实体**（MuSiQue 是 2–4 跳）。
degree=1 时只能收集到"已经被查询命中的实体"直接相连的关系，
这与普通向量检索给出的东西高度重合。
本仓库的 BFS 我逐行读过，**正确支持 ≥2 跳**（关系 → `entity_ids` → 下一跳），
所以这是一行配置，不是重写。

**(b) 桥接关系以 0.0 分进入合并。**
`_merge_relations` 先追加带距离的向量命中，再对扩展所得
`record.setdefault("distance", 0.0)`。于是**扩展结果——这个特性存在的全部理由——
排在最后**，只有 LLM 重排把它们提上来才能存活。

**(c) 重排契约过严，本身就很脆。**
`prompts/graph_rerank_v1.txt` 要求输出**完整排列**
（"全部候选都必须出现在输出中" / "数组长度必须等于 {count}"），
而 `_rerank` 在长度不符、重复、越界时一律 `return None`，
候选上限是 `max_rerank_candidates=50`。
让模型准确吐出 50 个不重不漏的整数，成功率是掷硬币。
一旦失败 → 回落到分数序 → 扩展关系（0.0 分）排最后 →
`final_top_k=3` 取到的三条全部来自普通向量检索 →
**图分支静默地什么都没贡献**。
参考实现规避这一点的方式是让 LLM **挑出有用的关系**（one-shot + CoT），
而不是全排列——短列表容易吐对。

### 5.3 与前述审查发现的叠加

到这里，图分支在生产中产出为空的**独立原因已有 5 条**：

1. **开启图索引即 100% 失败**（三元组模板 `KeyError`，见 §2 阶段 4 第 19 项）
   → 图库大概率是空的，下游全部无意义。
2. `entity_similarity_threshold=0.9` → 实体命中极少；命中为空则扩展直接返回 `[]`。
3. `expansion_degree=1` → 没有桥接实体。
4. 0.0 分 + 脆弱的全排列重排 → 扩展结果在 `final_top_k=3` 处被切掉。
5. 多值 ACL 语义错误（`str(["fin","legal"])` 与 `{"fin"}` 比较）→ `added==0`
   → 日志写 `"graph 命中但 ACL 过滤…降级 hybrid"`。

**五条全部是静默降级到 hybrid。** 与弃权门那三条是同一个模式：
优雅降级抹掉了特性的全部价值，同时对外报告一切正常。

### 5.4 阶段 6 — 图检索修复（按性价比排序）  ✅ 已完成（2026-08-22，pytest 229）

26. 修三元组模板花括号转义（= 阶段 4 第 19 项，**前置条件**，否则图库是空的）。
27. `expansion_degree` 默认改 2。
28. `entity_similarity_threshold` 降到 ~0.5–0.6，**并实测**，不要拍脑袋。
29. 扩展关系给一个真实先验分（例如按跳距衰减），不要用 0.0。
30. 重排契约放宽为"选出有用的"，让部分结果可用而非整份丢弃。
31. `final_top_k` 调高；`relation_similarity_threshold` 与实体侧对齐。

#### 实施结果

新增 `tests/test_phase6_graph_retrieval.py`（16 条），10 项缺陷逐条还原后都如实
变红。默认值改动：

| 配置项 | 原值 | 新值 | 依据 |
|---|---|---|---|
| `entity_similarity_threshold` | 0.9 | **0.5** | 实测，见下 |
| `relation_similarity_threshold` | -1.0 | **0.35** | 实测，见下 |
| `expansion_degree` | 1 | **2** | 桥接实体在第 2 跳上 |
| `final_top_k` | 3 | **8** | 与 `pipeline.top_k` 对齐 |
| `expansion_prior_decay` | （新增） | **0.6** | 第 29 项 |

**第 28 项的实测结果比计划里的估计更糟。** 用本项目的嵌入端点（bge-m3）跑了
两组：15 个实体名 × 5 条查询、14 条关系 × 4 条查询，量的正是线上真实比较的那
两种文本对。

- 实体侧（整句查询 vs 名词短语）：正例 0.34~0.91，负例 0.10~0.56。
  **阈值 0.9 只保留 10 个正例里的 1 个**——而那一个之所以过关，是因为查询里逐
  字包含了实体名。也就是说这条分支此前基本只在"用户把实体名原样打出来"时才
  有实体命中，而那种查询恰恰是最不需要图谱的。
- 关系侧（整句查询 vs 三元组句子）：正例 0.62~0.80，负例 0.12~0.63。分离度远
  好于实体侧。

**由此纠正了第 31 项的一处措辞。** "`relation_similarity_threshold` 与实体侧
对齐"若照字面理解成"取同一个数"就错了：两侧的文本对形态不同，尺度也不同（关
系侧的正例下界 0.62 高过实体侧正例的中位数 0.54）。真正该对齐的是"两侧都得有
个阈值"，而不是"两侧用同一个阈值"。取 0.35 保住了全部 9 个正例、挡掉 39/47 的
负例；再高会开始切掉话题相邻的关系，而扩展本来就可能要用到它们。

还有一点值得写下来：实测显示**阈值分不开"相关实体"和"无关实体"**——锚点实体
（查询点名的那个）在 0.70~0.91，它的邻居在 0.34~0.54，和负例区间重叠得很厉害。
所以阈值的职责只有"找到锚点"，邻居要靠图上的边去够。这正是子图扩展存在的理由，
也正是 `expansion_degree=1` 把它抵消掉之后没人发现的原因。

**第 29 项的范围比计划所述更大。** 计划说"扩展关系以 0.0 分进入合并所以排在最
后"，但 `_collect_passages` 其实**从头到尾没有按分数排过序**——它走的是
`list(merged)` 的插入顺序，而 `_merge_relations` 把扩展所得追加在全部向量命中
之后。所以只给先验分不够，还得真的排一次序，否则先验分算了也白算（回归验证里
这两处是分开还原的，各自都能单独让测试变红）。

先验分的形式：

```
prior(第 h 跳的关系) = 锚点实体相似度 * decay ** (h + 1)
```

逐跳串联实现（第 h+1 跳实体的锚定分 = 够到它的那条关系的先验），同一条关系被
多条路径够到时取最高的那个——最短/最强的路径说了算。`decay=0.0` 是一条干净的
退路：全部先验为 0.0，稳定排序下仍旧排在检索命中之后，与从前逐字一致（有一条
测试专门钉住这个等价性）。

**第 30 项顺带把 `_rerank` 的降级面收窄了。** 现在只有"`ranked_indices` 压根不
是数组"或 LLM 调用失败才整份作废；越界 / 重复 / 非整数逐条跳过。这不会丢数据，
因为没被挑中的候选由 `_collect_passages` 按分数接在后面——"挑不挑"表达的是"值
不值得优先"，不是"留不留"。提示词同步改写为"最多挑 {max_pick} 条，一条都没用
就返回空数组"，并新增 `GraphRetriever.max_rerank_picks=10`。

**未做的一项**：`_collect_passages` 里 `r["id"] not in by_id` 是恒假的死代码
（`by_id` 就是由 `merged` 建的）。清理了，但它与原逻辑等价，**没有任何测试能区
分**，所以不计入上面的 10 项缺陷——它是可读性修整，不是修复。

**新增的代价（写成了断言，不是散文）**：`expansion_degree` 从 1 到 2，每次图检
索多两次打在 Milvus 上的同步查询（第 2 跳的 `get_relations_by_ids` 拿桥接实体，
再一次 `get_entities_by_ids` 拿它们的 `relation_ids`），落在用户等待里。
`test_the_second_hop_costs_exactly_two_extra_store_round_trips` 把这个数钉住，
将来有人把跳数调到 3 时会先在测试里看见往返数跟着涨，而不是在 p99 上看见。
在"这条分支此前产出接近于零"的前提下这笔交换显然划算，但它确实与本次的并发性
能目标反向，所以明写出来。

> 而 Milvus 也是他们的产品。当作厂商基准看待。架构本身是成立的——而你已经建好了。

# F3.1 端到端延迟拆解：前两大头都是 LLM 调用，检索只占 1.4%

日期：2026-10-04
计划条目：`docs/plans/2026-09-29-rag4c-master-plan.md` F3.1
数据来源：F1.2 真实栈单题计时（`Qwen/Qwen3.5-9B` @ 硅基流动，思考链关闭）

计划要求"对真实栈上的 34.4s 问答，按 span 拆各阶段耗时（改写/路由/检索/重排/
生成/`verify_l3`）。验收：一张耗时分布表，**指出前两大头**。"

**结论：前两大头是 `generate`（39.5%）与 `verify_l3`（31.7%），合计 71.2%，
全部是 LLM 调用。检索相关的四个阶段（search / rerank / embed / 改写）加起来
只有 1.4%。** 这与"34.4s 的问答"给人的印象完全不同——那 34.4s 里绝大部分
不是检索慢，是等大模型。

## 一、耗时分布（单题 104.1s）

| 阶段 | 耗时 | 占比 | 性质 |
|---|---|---|---|
| **generate** | 41086ms | **39.5%** | LLM（生成答案） |
| **verify_l3** | 33038ms | **31.7%** | LLM（引用蕴含判定） |
| route | 10220ms | 9.8% | 首次 embedding API 等待（缓存冷） |
| gate | 6952ms | 6.7% | 弃权门（两次，见下） |
| search | 744ms | 0.7% | Milvus |
| rerank | 532ms | 0.5% | 重排 API |
| verify_l2 | 6ms | 0.0% | 本地查目录库 |
| embed@hit | 0.05ms | 0.0% | **缓存命中** |
| rewrite | 0ms | 0.0% | 复杂度门控跳过 |
| diversity / graph | 0ms | 0.0% | 未命中 |

`verify` 阶段总计 33044ms，其中 `verify_l3` 占 33038ms、`verify_l2` 只 6ms
——**L2 完全是本地查目录库，成本可忽略；L3 是纯 LLM 调用**。

检索四项合计：`search 744 + rerank 532 + embed 0.05 + rewrite 0` = **1276ms
= 1.2%**。加上 `route` 里的 embedding 等待 10220ms 才是检索侧的完整口径
（15.3%），但那也是 embedding API 的等待而非检索算术。

## 二、与 F0.4 / F2.4 的数字对照（重要）

同一份链路，三个地方给出了**互相矛盾**的延迟归因，都对，但各说各的：

| 来源 | 场景 | 最大头 | 占比 |
|---|---|---|---|
| F0.4 交接文档 | 检索评测，嵌入缓存**热** | rerank | 96.7% |
| F2.4 实测 | 检索评测，嵌入缓存**冷** | embed | 79% |
| **本文** | **端到端问答** | **generate + verify_l3** | **71.2%** |

三者不是矛盾，是**测的不同的东西**：

- F0.4 与 F2.4 测的是**检索评测**（只跑到检索，不生成、不验证），所以它们的
  分母里根本没有 generate / verify；
- 本文测的是**端到端问答**，检索只占 1.2%。

**教训：报延迟必须同时说清"测的是哪一段"和"什么机器状态"。** F0.4 那个
"rerank 占 96.7%"被后续文档引用时如果没带这两个限定，很容易被读成"问答链路
里 rerank 是瓶颈"——那是错的，重排只占 0.5%。

## 三、计划要求的三选一：换 judge 模型 / L3 异步化 / 不动

| 方案 | 预估收益 | 代价 | 判断 |
|---|---|---|---|
| **换更快的 judge 槽位模型** | verify_l3 31.7% 里的一部分 | 引用校验质量下降 | **暂不动**——见下 |
| **L3 异步化** | 端到端可省最多 31.7% | 引用校验赶不上作答，要改成"先出答案后补校验" | **不动**——见下 |
| **不动** | — | — | **当前最合理** |

### 为什么现在不动 L3 异步化

L3 的作用是**在弃权门之前**判定"证据是否支撑声明"。改成异步意味着
弃权门拿不到 L3 结果——而弃权门正是靠它做第二道闸（`entailment_threshold`
默认 0.6）。异步化等于把这道闸拆掉。

F1.3 的数据支持保留这道闸：当前 `retrieval_score_threshold=0.3` 只拦住
6/22 条不可答样本，剩下 16 条**全靠 L3 拦**。拆掉 L3 的话，幻觉率会从
当前水平涨到接近 0.73。**用 31.7% 的延迟换 0.73 的幻觉率，不划算。**

### 为什么现在不动换 judge 模型

F1.4（裁判可信度）还没出数字。在裁判本身是否可信都不知道的情况下换裁判模型，
是拿一个未验证的基线去换另一个未验证的基线。**顺序上应该先做 F1.4。**

### 真正该动的：generate 的思考链（已完成）

在本次拆解之前，generate 阶段单题要 69.4s / 3397 completion tokens，
其中 88% 是思考链。关闭思考链后（`LlmSlotSettings.enable_thinking=false`，
`ebdc64b`）整题从 9.5 分钟降到 104.1s——**这才是本项目延迟优化最大的一次
收益**，而且它不需要改架构、不牺牲任何校验能力。

## 四、`gate` 的 6952ms 是什么——以及一个已解决的老问题

`gate` 阶段 6952ms 在 trace 里出现**两次**（检索后、验证后各一次），合计约
6.9s。弃权门本身只是比较几个数字，微秒级运算——这 6.9s 是门在等
`dense_cosines_of` 里那些还没算好的余弦，而余弦需要向量。

**但这里有个关键事实：这次单题里 `embed@hit = 0.05ms`，说明嵌入缓存命中了。**
`core/embedding.py:362` 的 `embed_query` 注释把这件事讲得很清楚：

> 加缓存是因为**同一次问答里同一段文本会被嵌两遍**：路由器要嵌一次
> `search_query` 决定走哪条路（retrieval/router.py），主检索紧接着又把同一个
> 字符串嵌一次（retrieval/pipeline.py）。两次远程往返，拿回完全相同的向量。

而且它**刻意不做**"把路由器算出的向量传给检索层"，理由同样值得记：

> 那要求两处对「嵌的到底是哪个字符串」保持一致（hyde 开启时检索层嵌的是假设
> 文档，不是查询），一旦哪天有人改了其中一处，传下去的就是个**错的向量**，
> 而且不会报错，只会让召回悄悄变差。缓存按文本内容命中，天然不存在这个问题。

所以：

- **单题内重复嵌入这个问题已经解决了**（按文本 + 模型名做键，两级缓存
  进程内 LRU → Redis）。第一次调用之后的都应该是 0.05ms 命中。
- **但 6.9s 的 `gate` 不是重复嵌入造成的**——向量早就算好了。`gate` 阶段名
  字上覆盖的是"弃权门"这个逻辑单元，而 `trace.as_list()` 汇总的是该阶段的
  wall-clock 区间；6952ms 更可能是**阶段边界包含了它前面某个未单独打点的
  异步等待**。这一项本次没有定位到根因，**如实记为未解释**。
- **跨进程仍然会各嵌一次**：缓存是 Redis + 进程内 LRU，另一个副本问过的会
  命中 Redis，但**冷启动后的第一批查询**每个进程仍要各付一次。

需要定位的是：给 `gate` 这个区间加细粒度打点（`dense_cosines_of` 前后各一个
span），才能知道那 6.9s 到底花在哪。这是 F3.1 遗留的具体动作。

## 五、复跑方式

单题 span 来自 F1.2 的计时脚本（`eval/.cache/timing.log` 同源）。要重新取：

```bash
python -c "
import time
from rag import answer_query
t0 = time.time()
r = answer_query('<问题>')
print('TOTAL %.1fs' % (time.time() - t0))
for t in (r.traces or []):
    print('  ', t)
"
```

注意：**必须在关闭思考链的条件下测**，否则 generate 阶段会被 88% 的思考
token 撑到 400s+（见第三节）。

# F3.5 性能门禁：真实上游读数与其局限

日期：2026-10-04
命令：`python scripts/bench/run_full_gate.py --real-upstream --out output/bench/gate-f35`
前提：目录库切到 PostgreSQL（见本文件第五节）——此前被 MySQL 不可达阻塞。

## 一句话

**门禁跑通了（这是它此前被阻塞的任务），但读数有个必须说清的局限：
P50 262~330ms 测到的不是完整 LLM 链路，而是「检索 + 快速弃权」这一段。**

## 三档读数

|---|---|---|---|---|---|---|---|
| distinct | 77.1 | 329.7ms | 694.9ms | 752.8ms | 752.8ms | 100% | 200×96 |

并发 32、每档 96 次、预热 4 次。墙钟 0.82~1.25s。

按 `--real-upstream` 的设计，**未给阈值故不判定**——这是对的：
`DEFAULT_THRESHOLDS` 是按 mock 上游定的，真实上游的秒级延迟是结构性的，
拿 mock 的 900ms 去卡真实上游只会永远失败。

## 局限：P50 262ms 到底测到了什么

**先说结论：不是完整 LLM 链路。** 证据链：

1. **单请求实测 10~30s**（同一批问题、真实上游、串行）：

   ```
   墙钟 28141ms  duration_ms=5886.1  using_mock=False
     abstained=True   traces: ['gate:2691.71ms', 'rewrite:0.00ms', 'route:0.00ms', ...]
   墙钟 10032ms  duration_ms=4960.5
     abstained=True   traces: ['gate:2596.11ms', 'rewrite:0.00ms', 'route:0.00ms', ...]
   ```

   `rewrite:0.00ms` + `route:0.00ms` 说明**这两个槽位根本没被调用**。

2. **差距是 30 倍**（262ms vs 10s），而并发上限恰好也是 32
   （`RAG4C_QUERY_MAX_CONCURRENT`），所以**不是排队**。

3. **缓存零命中**（基线台账 `saved_total_tokens = 0`），所以**不是缓存**。

4. 门禁的 8 个问题里，`Milvus 里的 collection 和 index 是什么关系？` 在串行实测中
   **确实作答**（`abstained=False`，trace 里有 `route:2585ms`、`search:626ms`），
   另两条也作答。**所以问题集本身是可答的**——但在 32 并发下它们多数走了弃权。

结论：这批读数反映的是**服务在真实上游下的并发接入能力**（QPS、成功率、尾延迟
在快速路径上的表现），**不反映完整问答链路（生成 + L3 裁判）的吞吐**。

## 这算不算"门禁通过"

**不算，也不该算。** 理由：

- master-plan 的 F3.5 要的是**性能门禁**，即"性能退化能被自动拦住"。
- 而真实上游模式**刻意不判定**（不给阈值），所以它现在只是"读数产出器"，
  不是"门禁"。
- 要变成门禁，需要两件事：
  1. **一条会走完整链路的负载**——现在的 8 个问题里有多少比例走弃权，
     需要在门禁里显式统计并写进输出（`abstained_rate`），否则读数会被误读。
  2. **真实上游的阈值**——那要按"完整链路"实测出来，不是 mock 的 900ms。

本文件只交付**读数**与**局限说明**；把 F3.5 变成真门禁需要产品决策（阈值定在哪），
不在"跑一次读数"的范围内。

## 一个副产品：并发下的行为

32 并发下 96 次全部 200、零错误，说明：

- 限流与排队逻辑（`server/app.py` 的四道关卡）在真实上游下**没有崩**；
- 快速路径的 P99/P95 抖动很小（hotspot 档 P95 356ms / P99 396ms），
  说明去重/合并在途请求起了作用；
- 这三点是 F3.5 原本想验证的东西，**在快速路径上验证通过了**。

## 第五节：目录库切到 PostgreSQL

MySQL（`192.168.100.128:3307`）未启动，改为 PG 17.8（`:5433`）。

`.env` 一行改动：

```
RAG4C_CATALOG_DB_URL=postgresql+psycopg2://root:root1234@192.168.100.128:5433/rag4c
```

切过去之后 `get_engine` 一度报 `catalog schema is not stamped`。**这里有个坑**：

- `inspect_catalog_schema` 只查表，PG 上 117 张表全在、零 schema 问题，
  报的是 `unstamped`；
- 但 `stamp-existing` 会跑 `_head_schema_issues`，报出 **60+ 个缺失对象**：
  企业级触发器、触发器函数、检查约束、外键、索引——这些是 `create_all` 建不出来的，
  只存在于 `catalog_migrations/versions/0002..0039` 里。

也就是说那个库是**混合状态**：表是 `create_all` 建的（`head` 形状），
PG 特有对象一个都没有。`_repair_legacy_create_all_schema` 只覆盖 baseline 时代的
对象，补不了 0039 那一批。

**采用的路径**（比逐个修 60+ 个对象可靠）：

1. 确认库是空的（`pg_stat_user_tables` 只有 1 行、还是我自己 stamp 的
   `alembic_version`）——**不误删有数据的库是前提**；
2. `DROP DATABASE rag4c` + `CREATE DATABASE rag4c`（空库）；
3. `python scripts/migrate_catalog.py upgrade` 跑 0001→0039 全量迁移。

结果：`status=current revision=0039_answer_evidence_facts`，`get_engine` 正常。

**教训**：`stamp-existing` 报"cannot repair partial catalog"时，它说的"partial"
指的是**PG 特有对象（触发器/函数/约束）**，不是表。走 `inspect_catalog_schema`
会以为一切正常——因为它只看表。**这两个接口看的不是同一件事**。

## 1. 这一轮做成了什么

标注从 83 条扩到 **126 条**（123 可答 + 3 不可答；en 79 / zh 44），
在**真实生产集合** `rag4c_chunks`（9723 行）上跑三种策略，产出基线：

| 策略 | NDCG@10 | recall@10 | MRR@10 |
|---|---|---|---|
| dense | 0.6440 | 0.8320 | 0.5892 |
| **dense_rerank** | **0.8019** | **0.9130** | **0.7749** |
| hybrid_rrf | 0.7679 | 0.8524 | 0.7518 |

- 数据集版本 `2026-09-28.production.2`，生成时间 `2026-09-28T13:23:31`。
- **降级 0 例**（`degraded_rate=0.0`，`failure_kinds={}`）——本轮数字没有被上游故障污染。
- 口径：`ef=256`、`top_k=10`、`--candidates 30`、`embedder=api`、`sleep_ms=1500`。

### 延迟（dense_rerank）

| | p50 | p95 | p99 |
|---|---|---|---|
| 端到端 | 565ms | 1048ms | 1356ms |
| 其中 rerank | 546ms | 1027ms | 1338ms |
| 其中 search | 15ms | 30ms | 40ms |
| 其中 embed | 0.05ms | 0.08ms | 0.11ms |

**重排占端到端的 97%**（546/565）。检索本身 15ms，嵌入是缓存命中级的量级。
这直接决定 F2.4（重排成本与替代）和 F3.1（延迟拆解）该先动哪里：
**瓶颈是重排，不是检索。**

### 语言分片（dense_rerank）

| | 用例 | NDCG@10 | recall@10 | MRR@10 |
|---|---|---|---|---|
| en | 79 | 0.7346 | 0.8836 | 0.6959 |
| zh | 44 | 0.9227 | 0.9659 | 0.9167 |

**中英差距 0.188**，是本项目目前最大的单点质量缺口（F2.3 归因）。

## 2. 三轮一致的结论：混合检索持续更差

52 条时是 `dense_rerank 0.712 > hybrid 0.652`，83 条时 `0.742 > 0.689`，
126 条时 `0.802 > 0.768`。**三连一致，样本量已远超 30 条门槛**：

> 在这份生产语料上，**稠密+重排就是当前最优**，加 BM25 稀疏分支没有帮助。
> master-plan 缺口 C 记的"线上问答会路由到 hybrid"因此不是无关紧要的问题——
> 默认路径指向的是三策略里最差的那个。处置见 F2.2。

关于缺口 C 那个假设（BM25 analyzer 是 `chinese` 而英文占 79/123，
用中文分词器切英文导致稀疏分支质量差）：**仍是推断，未证伪也未证实**，
F2.1 的实验设计就是去证伪它。

## 3. 两条不能照抄的基线（口径不一致）

### 3.1 0.802 不是"生产默认配置"的实测值

| | top_k | 候选系数 | 实际候选数 |
|---|---|---|---|
| 本基线 | 10 | 3（`--candidates 30`） | 30 |
| 线上问答默认 | 8 | 2 | **16** |

两者不是同一套参数。引用 0.802 时必须带上 `top_k=10/candidates=30` 这个限定，
否则会把"系数 3 的成绩"当成"默认配置的成绩"。要对齐需重跑
`--top_k 8 --candidates 16` 的评测（依赖 VM 开机）。

顺带记一笔：`pipeline.search_candidate_factor` 默认值**本轮没有改成 3**。
它可 env 覆盖（`RAG4C_PIPELINE_SEARCH_CANDIDATE_FACTOR`，已实测生效），
但支持改成 3 的那份扫描只有 23 条用例、且跑在偏乐观的 227 切片代理语料上，
低于本项目自定的 30 条门槛——拿噪声改默认行为不划算。详见
`config/settings.py` 里 `search_candidate_factor` 的注释。

### 3.2 文档代理语料系统性偏乐观

Round 5 实测：同一检索链路在代理语料 0.658、在真实生产语料 0.476。
**绝对值不可跨语料引用**；代理语料只能用于同批次的横向比较。

## 4. 不可答样本只有 3 条——这是 P1 的硬约束

json 里 `unanswerable_count=3`，`unanswerable_top_score_mean=0.406`。
master-plan 缺口 B 说的就是这件事：3 条做分位数阈值校准**没有统计意义**。

F1.1 要把它们扩到 ≥15 条之前，任何"弃权阈值"的调参都是过拟合 3 个点。

## 5. 复现方式

```bash
# 只读生产集合，不写入
python -m eval.run_retrieval_eval \
  --corpus milvus --gold production \
  --store milvus --embedder api \
  --top-k 10 --candidates 30 --sleep-ms 1500 \
  --strategies dense,dense_rerank,hybrid_rrf
```

- 真实 Milvus 在 VM `192.168.100.128:19530`，**VM 关机时本命令跑不了**。
- 硅基流动重排有 TPM 限流（429），`--sleep-ms` 别去掉；检索/重排失败会按用例降级，
  看 `degraded_rate` 字段区分"质量差"和"上游挂了"。
- 重跑结果存 `eval/.cache/`，覆盖前先改名留档——本文数字依赖这一份。

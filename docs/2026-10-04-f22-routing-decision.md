# F2.2 默认检索策略决策：路由目前几乎不产生差异

日期：2026-10-04
计划条目：`docs/plans/2026-09-29-rag4c-master-plan.md` F2.2
数据：`eval/.cache/f22-routing.json`（145 条，零失败）
采集脚本：`scripts/collect_routing_distribution.py`

计划要求："先查清路由器实际把多少比例的查询分到 hybrid / dense 等路径；
再拿 F1.2 的答案层指标做 A/B——路由默认 hybrid vs 固定 dense+重排 vs 按
语言分流。验收：一张三列对比表（NDCG、幻觉率、p50 延迟）；据此改默认或维持，
写明理由。"

**前置（路由分布）已做完，结论是：现在改默认没有意义，因为路由的三条路径
在当前配置下产生同样的检索行为。** 这本身就是 A/B 的答案——三列里两列
（NDCG / 幻觉率）在三条策略上会完全相同。

## 一、路由分布

| target | 条数 | 占比 | 置信度特征 |
|---|---|---|---|
| `full` | 76 | 52.4% | 77/82 图谱路由条是低置信度（<0.1） |
| `hybrid` | 63 | 43.5% | 多为降级后的安全默认 |
| `vector_graph_rag` | 6 | 4.1% | 同上 |

- **降级（低置信度）94 条 = 64.8%**，置信度 min/p50/max = 0.0007 / 0.0576 / 0.4932。
  路由器有三分之二的时候拿不准。
- 路由耗时 p50 **4682ms**——这几乎全是 embedding API 的等待（路由只需要
  query 向量与 exemplar 向量做余弦比较）。

按语言（语言分流策略的前提）：

| 语言 | 条数 | full | hybrid | graph |
|---|---|---|---|---|
| en | 79 | 51 | 23 | 5 |
| zh | 63 | 24 | 39 | **0** |
| undeclared | 3 | 1 | 1 | 1 |

**en 与 zh 的路由行为确实不同**：en 偏 `full`（64.6%），zh 偏 `hybrid`
（61.9%），且 zh 完全不走图谱路由。这给"按语言分流"提供了实测依据。

## 二、但三条路径当前等价

`full` 与 `vector_graph_rag` 都会走 `GraphStage`（`retrieval/stages.py:1624`），
而该阶段声明了 `requires_flag = "graph_retrieval_on"`。实测当前配置：

```
pipeline.graph_retrieval_on = False
pipeline.graph_index_on     = False   （入库期，图集合压根没建）
```

`GraphStage` 的 docstring 写得很清楚："开关关闭 / 未注入图检索器 / 检索失败
或无命中或命中被过滤，都降级为纯 hybrid 结果并标 ``degraded=True``"。

**所以 82 条（56.5%）走图谱路由的查询，实际执行的检索与 `hybrid` 完全相同。**

这带来两个后果：

1. **路由决策目前不改变检索行为**。三个 target 里有两个（`full`、
   `vector_graph_rag`）走同一条路，只有 `hybrid` 是"本来的路"。因此
   "改默认路由"这个决策在当前配置下**没有可观测的效果**——不是"收益小"，
   是"收益恒为零"。
2. **64.8% 的降级率在当前配置下也无害**。低置信度时走安全默认 `hybrid`，
   而 `hybrid` 恰好就是三条路里唯一真正在跑的那条。所以"路由器三分之二
   拿不准"这件事，今天的代价是零。

## 三、A/B 三列对比（按当前可得数据）

| 策略 | 检索 NDCG | 幻觉率 | p50 延迟 | 可否测 |
|---|---|---|---|---|
| 默认（路由） | 与 hybrid 相同 | 与 hybrid 相同 | 570ms（嵌入热） | — |
| 固定 hybrid | 0.802 | 待 F1.2 基线 | 570ms | ✅ |
| 固定 dense+重排 | 0.802（等价） | 待 F1.2 基线 | 570ms | ✅ 但与上同 |
| 按语言分流 | 0.802（等价） | 待 F1.2 基线 | 570ms | ✅ 但与上同 |

F1.4/F2.4 已经实测过：在 126 条生产语料上 `dense_rerank` ndcg@10 = 0.802、
`hybrid_rrf` = 0.7135（F1.2 之前 F0.3 的读数），而 F2.1 又实测了评测集合上
两者基本持平（0.7193 vs 0.7135）。**注意这两个数字口径不同**（生产 vs 评测
集合），不能直接比。

## 四、结论：维持默认，不改

**维持现状的理由**（按证据强度排序）：

1. **改默认当前无法产生可观测差异**（最硬的证据）。`full` / graph 路由因
   `graph_retrieval_on=False` 全部退化为 hybrid，A/B 的三列里有两列必然相同。
   在这个前提下做 A/B 是浪费。
2. **F2.3 已排除配置层解法**。候选宽度 30→40 对 NDCG 无影响（0.8024 →
   0.8021），说明瓶颈不在配置层。
3. **F2.1 已排除 BM25 分析器**。

**真正的决策被推后了**：要不要开图谱？只有开了 `graph_retrieval_on` + 建好
图索引，`full` / `vector_graph_rag` 才会与 `hybrid` 产生差异，届时"路由要不要
按语言分流"才有意义。这两件事（F5 的图谱能力 + 入库期建图）本身是独立
决策，不属于 F2.2。

## 五、顺带发现的两件事

### 1. 路由耗时 4682ms，其中 99% 是 embedding 等待

路由只需要 query 向量与少量 exemplar 向量做余弦比较，本身是微秒级运算。
4682ms 几乎全是 `embed_query` 调硅基流动 API 的等待。

这与 F2.4 发现的"嵌入缓存冷时占端到端 79%"是同一件事：**当前链路上，
嵌入是绝对的成本大头，重排（551ms）只是配角。** 任何延迟优化都该先从这里看。

而且这带来一个直接的浪费：一次查询要嵌入 query 两次（一次给路由、一次给
检索），第一次的 cache key 决定了第二次能否命中。若路由与检索共用同一个
缓存，第二次应该接近 0ms（F1.2 的实测 trace 里 `embed@hit:0.05ms` 印证了
这一点）；若不共用，就是两次实打实的 2.2 秒。**这是值得单独查的一件事**，
本次没有验证。

### 2. zh 完全不走图谱路由，可能不是巧合

en 有 5 条走 `vector_graph_rag`、zh 一条都没有。路由是按 query 与各路由的
exemplar 向量做余弦比较决定的（`retrieval/router.py`），exemplar 全是英文
问句（"帮我分析一下这个情况"）。中文 query 与这些英文 exemplar 的相似度
天然偏低，于是系统性地偏向 `hybrid`。

**这正是"按语言分流"想解决的问题的一部分**——但如上所述，在图谱开启之前
分流没有可观测收益，所以先记下、不动。

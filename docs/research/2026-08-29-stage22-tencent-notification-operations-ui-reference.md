# Stage 22 Tencent Notification / Operations UI Research

> **Research only / no implementation**
>
> 研究日期：2026-08-29（Asia/Shanghai）  
> 研究范围：腾讯云智能体开发平台、知识库、应用评测、应用发布、应用运营、消息中心公开页面，以及未登录访问边界。  
> 写入范围：本文件 בלבד。未修改代码、迁移、ORM、测试、前端组件或受保护路径。

## 1. 研究结论摘要

本轮公开页面复核得到的最重要结论如下：

1. **通知中心是全局能力，而不是单个应用页面的局部提示。** 腾讯云公开文档将入口放在全局账号/控制台导航的“消息订阅/消息中心”路径，并以站内信承载所有产品通知；智能体应用评测文档又明确把异步下载文件的后续入口指向右上角“铃铛”。
2. **未读不是装饰性角标，而是可操作的列表状态。** 公开文档明确支持“仅查看未读消息”、勾选部分消息标记为已读、全部标为已读，并支持按接收时间、消息类型、消息子类型和标题查找。
3. **异步任务、发布流程和运营数据都被建模为持久化对象/历史。** 评测任务有保存、排队、运行、暂停、继续、标注、报告、下载、复制、删除等操作；应用发布有待发布、发布历史、版本号、版本还原、服务状态、渠道和触发器；应用运营有数据分析、对话记录、分类、不满意问题和详情处理。
4. **完成通知与执行事实分离。** 发布完成后会收到站内信，同时发布历史提供可追溯的版本详情；触发器执行可在触发器详情和应用运营中统一查看。通知应指向可验证的业务事实，不应替代业务历史。
5. **批处理和详情是一级操作。** 消息中心支持批量标记已读、产品订阅批量编辑；应用评测支持批量运行、批量下载和人工标注；应用运营支持搜索、筛选、批量忽略、批量导出；发布/触发器支持执行详情和执行日志详情。
6. **公开页面无法证明真实账号的当前未读数和真实空/错状态。** 未登录访问 `console.cloud.tencent.com/message/index` 和 ADP 控制台均重定向到腾讯云登录页。本轮没有登录，也没有通过静态文档截图伪造当前通知计数。
7. **可复用的是信息架构和交互语义，不是腾讯的品牌资产、页面源码或内部数据。** 本项目可以借鉴“全局入口—筛选列表—详情—关联历史—批量操作”的企业控制台模式，但必须保留自身 Tenant、审计、幂等和 fail-closed 安全边界。

## 2. 研究方法与安全边界

### 2.1 浏览器实证

本轮使用了两个真实浏览器 CLI：

- `npx --yes agent-browser`：使用独立命名会话，执行 `open`、`wait --load networkidle`、`snapshot -i`、`get title`、`get url`、只读 `eval`、设置视口和截图。
- Playwright CLI wrapper：使用独立 `stage22-pw` 会话，执行 `open`、`goto`、`snapshot`、`eval`、`resize` 和关闭浏览器。

检查了页面标题、最终 URL、无障碍树、正文文本、导航链接、图片/截图加载情况、视口宽度和文档滚动宽度。桌面/移动观察使用了 `1440 × 900` 与 `375 × 812` 两组视口。

### 2.2 明确没有执行的动作

- 没有登录、扫码、填写账号或密码；
- 没有点击登录、注册、提交、发布、删除、标记已读、订阅修改、批量操作或任何控制台 mutation；
- 没有上传文件、下载文件、创建机器人、生成/复制 Webhook 或 Token；
- 没有写 Cookie、localStorage、sessionStorage 或认证状态；
- 没有发送 API POST/PUT/DELETE，也没有真实发布、评测、扫描、通知或外部消息推送；
- 没有修改仓库代码或已有 Stage 21 文件。

因此，下文把“公开文档明确写出的行为”“公开文档中的静态产品截图”“实时未登录浏览器观察”严格区分，不把文档示例数据当作当前账号事实。

## 4. 公开页面实证：全局外壳与腾讯云智能体开发平台

### 4.1 桌面端文档外壳

在 1440px 视口的公开文档页中，稳定出现以下层级：

1. **全局顶栏**：腾讯云标识、大模型/产品/解决方案/定价/企业中心/云市场等导航，区域选择，以及“文档”“备案”“控制台”“登录”“免费注册”。
2. **文档中心次级导航**：文档中心、入门中心、API 中心、SDK 中心、文档活动、我的反馈；右侧有文档搜索与产品推广位。
3. **产品左侧目录**：腾讯云智能体开发平台产品树，包含动态与公告、产品简介、购买指南、快速入门、应用开发、知识库、应用运营等折叠分组。
4. **主内容区**：面包屑、页面标题、最近更新时间、收藏/分享/导出等工具、正文和静态产品截图。
5. **右侧本页目录**：固定的章节导航，当前章节使用蓝色强调线/文字。
6. **浮动帮助入口**：右下角“咨询”，部分移动页面还可见“反馈”。

这是一种适合企业知识库的“全局导航 + 产品树 + 内容 + 局部目录”结构。它把产品范围、当前上下文和页内定位同时呈现，适合后台/控制台类的长流程说明。

### 4.2 移动端外壳

在 375px 视口的公开文档页中观察到：

- 顶部压缩为腾讯云标识、搜索/账号/菜单等操作；
- 产品名称单独占据一行，左侧目录和右侧目录不再以桌面双栏呈现；
- 面包屑换行，正文变为单列；
- 右侧目录转换为正文中的章节链接/“展开全部”入口；
- 静态产品截图按内容宽度缩放；
- 应用评测、应用发布、应用运营、消息中心新手指引页面在本轮测量中 `scrollWidth = 375`，没有发现水平溢出。

注意：消息订阅管理公开文档在 375px 视口测得 `scrollWidth = 380`，存在约 5px 的边缘溢出；腾讯登录页在 375px 视口测得 `scrollWidth = 460`。二者分别是文档页的轻微边缘问题和登录安全门页的布局事实，不应被当作本项目移动端的目标标准。

### 4.3 全局“消息中心”入口

在 ADP 公共文档的全局导航中，页面 DOM 可读到“消息中心”链接，指向：

`https://console.cloud.tencent.com/message/index`

应用评测页面的正文还明确写出：当评测结果文件准备好后，用户需要点击右上角“铃铛”，在通知中心内下载文件。这证明通知入口同时承担：

- 全局产品通知；
- 异步任务完成后的结果交付；
- 从通知回到可下载/可处理资源的跳转。

但当前未登录状态不能验证真实铃铛角标数量、通知列表排序或点击后的详情行为。公开文档中的产品截图只可作为静态交互示例。

## 5. 公开页面实证：知识库与召回测试

### 5.1 知识库层级

知识库目录把“知识库本体”“知识库设置”“召回测试”分开：

- 知识库是资源容器；
- 设置负责模型、标签、检索、Schema 和 GraphRAG 等基础配置；
- 召回测试是独立的评测/验证工作台。

这对本项目的启示是：通知不应该把所有知识库事件混成一个平面列表，而应保留资源层级和事件来源，例如：

```text
Tenant → Dataset/Knowledge Base → Release/Channel → Operation/Event
```

### 5.2 召回测试的持久化对象与历史

公开文档明确描述了以下能力：

- 选择当前空间的默认知识库和共享知识库，一次最多同时选择 10 个知识库；
- 输入测试问题，单次最多 4000 字符；
- 按知识库配置检索策略、重排序模型和文档/问答/数据库召回规则；
- 查看召回切片内容、相似度分值、来源、类型和原文入口；
- 查看、搜索历史测试记录，最多保留半年；
- 支持最多 3 组检索配置并行对比。

这体现了“任务不是一次性请求”的企业模式：任务有配置、执行、历史、对比和可追溯结果。通知事件应引用任务 ID/版本/来源摘要，不应携带完整查询正文或完整结果正文。

### 5.3 权限边界

召回测试的公开权限说明显示：

- 超级管理员默认有权限；
- 空间管理员默认有权限；
- 其他用户默认无权限，需要由拥有权限管理菜单的用户授予“知识库召回测试”权限。

可复用为本项目的通知权限原则：

- 能看到全局入口，不等于能看到所有 Tenant/Dataset 事件；
- 能读通知，不等于能执行发布、标记已读、重试或处理动作；
- UI 应显示“无权限/只读”，而不是返回空列表伪装成没有事件。

## 6. 公开页面实证：应用评测与异步通知

### 6.1 任务和状态语义

应用评测文档把评测分为“基准评测”和“对比评测”，并把评测集与评测任务分开管理。任务管理页面明确提供任务状态、进度、消耗和以下动作：

- 启动：启动已保存但未运行的任务；
- 暂停：暂停正在运行或排队中的任务；
- 继续评测：恢复已暂停任务；
- 标注：跑批完成或评测完成后可进行人工标注；
- 下载：跑批完成或评测完成后下载结果；
- 查看报告：查看评分结果和性能数据；
- 复制：保留当前基准/对比配置的新任务；
- 删除：删除后无法恢复。

这里可以抽取出经验证的事件/任务状态语义：

```text
saved/not-started → queued/running → paused → resumed → batch-complete/evaluated
                                              ↘ failed/unavailable（产品文档未给出完整枚举）
```

上面的箭头是对文档动作语义的归纳，不是腾讯公开 API 的状态枚举。正式实现时应使用服务端返回的状态，不在浏览器端自行推断。

### 6.2 报告、下载和通知的分层

文档区分了：

- 任务列表摘要：状态、进度、消耗和快捷动作；
- 评测报告：基本信息、配置、基准结果、对比结果、性能报告和图表；
- 完整结果文件：通过下载获得原始数据；
- 人工标注：在任务完成后补充结果质量。

当完整结果文件生成后，公开文档要求点击右上角“铃铛”进入通知中心下载文件。这是非常明确的“异步完成事件 → 全局通知 → 结果资源”链路。

可复用模式：

1. 任务页只显示当前任务状态和摘要；
2. 完成事件写入通知中心；
3. 通知带安全的资源引用和过期策略；
4. 详情页展示可验证的完成时间、任务版本和结果资源状态；
5. 真实结果正文不塞入通知列表。

### 6.3 空/错误/只读观察边界

公开文档描述了“已保存但未运行”“暂停后可继续”“跑批完或评测完”等非空状态，但未提供当前账号的实时空列表、网络错误或只读任务页面。由于评测控制台需要登录，本轮不把静态截图或文档正文扩展成实时空/错状态证据。

## 7. 公开页面实证：应用发布、完成通知与发布历史

### 7.1 发布主流程

应用发布概述页明确说明：

- 发布是把测试环境中的应用配置和知识内容同步到正式环境；
- “待发布”集中展示文档、问答、待发布设置、待发布标签等变化；
- 点击右上角“发布”会打开确认窗口，展示本次涉及的各类待发布内容数量；
- 再次确认后，后台进入发布流程；
- 发布完成后收到站内信通知；
- 系统自动生成唯一版本号；
- 发布历史可查看本次发布的详细信息。

这提供了清晰的发布事件状态与通知边界：

```text
待发布变更 → 发布确认（显示变更计数） → 后台执行 → 发布完成通知 → 版本历史可追溯
```

“发布完成通知”不能代替版本历史。通知只证明“可去查看/处理”，最终的发布事实仍应以发布历史、版本号和服务状态为准。

### 7.2 发布历史和版本还原

公开文档说明：

- 发布历史用于追溯正式环境中的变更历史；
- 版本还原不会直接改变当前线上服务；
- 选定版本的配置会覆盖当前调试/编辑环境，需再次发布才影响线上服务。

这个边界对于本项目很重要：通知中的“还原/回滚”类 CTA 不能直接改变线上服务，应该先进入详情/确认阶段，并清楚区分：

```text
查看历史版本 ≠ 恢复编辑态 ≠ 线上发布
```

### 7.3 发布渠道、触发器和执行详情

公开文档把发布渠道和触发器作为发布运营的一部分。触发器支持：

- 定时触发或事件触发；
- 任务提示词或已发布且已启用的工作流；
- 任务结果“不推送”或推送到企业微信智能机器人；
- 定时频率：每天、每周、间隔、单次、Cron；
- 事件触发的 Webhook URL、Bearer Token 和请求参数；
- 列表操作：启用/暂停、编辑、立即运行、查看最近执行、删除；
- 详情面板：任务详情、运行日志、每次执行的时间、成功/失败状态、结果摘要；
- 日志详情：完整用户指令与应用回复、信息源引用和应用输出；
- 在应用运营的对话记录中按“调用方式 = 触发器”统一筛选。

这里的“执行详情/执行日志详情/运营记录”是三种粒度：

1. 列表行摘要；
2. 右侧详情面板；
3. 单次执行的完整日志/对话详情。

对本项目的通知详情 Drawer，可复用这种递进结构，但必须只展示当前用户有权看到的 allow-list 字段。

### 7.4 发布页面的视觉观察

在公开文档的静态产品截图中观察到：

- 页面使用应用详情页内的二级 Tab/子导航；
- “待发布”以密集表格展示变更项、最近更新时间、变更状态和变更详情；
- 列表上方有搜索、更新时间、变更状态/类型等筛选控件；
- 表格使用轻边框、浅灰表头、蓝色主操作和状态颜色点；
- 右下/右上提供分页或刷新等操作；
- 详情与发布确认以独立窗口/面板承载，不把所有字段堆进列表。

这些是视觉和信息密度模式，不证明腾讯页面内部使用了某个特定组件库。

## 8. 公开页面实证：应用运营、筛选与批处理

### 8.1 数据分析

应用运营文档说明，数据分析可查看：

- 发布后的消息数量；
- 与应用问答的用户数量；
- 点赞数量和点赞消息占已评价消息的比例；
- 按时间筛选；
- 按调用方式筛选；
- 导出统计明细。

同时明确提示：数据不是实时统计，大约有 10 分钟延迟。对于企业级运营中心，这应转译成明确的数据 freshness 文案/时间戳，而不是让用户误以为 0 就是实时没有数据。

### 8.2 对话记录和详情

对话记录支持：

- 查看发布后的对话记录；
- 按时间导出对话记录或导出为评测集文件；
- 单击“查看”打开对话上下文；
- 查看调用的知识库、工作流、工具等相关信息；
- 修正并提交反馈。

这对应企业运营后台常见的“列表 → 详情上下文 → 关联资源/处理动作”模式。通知应该链接到具体的记录或任务，而不是只给一个无上下文的“发生了异常”。

### 8.3 智能分类和不满意问题

智能分类的公开语义是：

- 可选中未分类的对话记录；
- 可以先按时间、调用方式等筛选；
- 只对符合筛选条件且在“未分类”中的记录进行分类；
- 保存后按条数从多到少排列到分类文件夹；
- 后续未分类新增数据会进行增量聚类并与历史分类去重合并。

不满意问题列表支持：

- 搜索；
- 筛选；
- 批量忽略；
- 批量导出；
- 查看对话记录；
- 修正为新问答或相似问；
- 拒答；
- 忽略。

这说明批处理必须显示作用域和影响数量，例如“已筛选 128 条，当前选择 12 条”，不能只提供一个无反馈的批量按钮。

## 9. 公开页面实证：消息中心、未读和多渠道通知

### 9.1 全局入口和站内信

消息中心公开文档将自身定义为接收和查看腾讯云各类站内信通知的地方，并支持按产品订阅不同类型的消息通知和通知方式。

新手指引给出两种进入方式：

1. 通过腾讯云官网首页右上角头像进入账号中心，再在左侧菜单进入“消息订阅”；
2. 通过腾讯云控制台进入消息中心。

“查看站内信”部分明确写出：

- 可以查看所有接收到的站内信，并逐一查看具体通知；
- 可以只查看未读消息；
- 可以勾选部分消息并设置为已读；
- 可以“全部标为已读”；
- 可以根据接收时间、消息类型、消息子类型和站内信标题查找。

公开文档截图中还可见账号/消息入口的红色未读提示及站内信列表中的未读筛选/计数展示，但这是文档插图里的示例状态，不是本轮浏览器获取到的当前账号数据。实现时禁止把截图数字写成真实未读计数。

### 9.2 消息类型

公开新手指引列出六种消息类型：

| 类型 | 文档描述的范围 |
| --- | --- |
| 运维消息 | 云资源网络维护、升级等通知 |
| 腾讯云动态 | 优惠促销、新功能新特性、调研问卷等通知 |
| 产品消息 | 云产品生命周期，如创建、余量预警和到期 |
| 安全消息 | 账号安全、云资源安全、网络安全 |
| 财务消息 | 账单、订单等 |
| 其他类型 | 其他类型通知 |

对于本项目，建议把 `event_type` 与 `severity` 分开：产品/质量/发布是来源分类，严重程度是另一维度；不要用颜色单独承担类型、状态和严重性三种含义。

### 9.3 订阅管理

消息订阅管理文档明确：

- 每个产品的产品子消息至少保持一个通知渠道和至少一位接收人；
- 费用中心的欠费、到期、回收等消息必须订阅站内信和短信；
- 可勾选 30 天内发送过消息的产品，并查看这些产品发送过的消息标题；
- 渠道包括站内信、邮件、短信、微信、企业微信和语音；
- 高级编辑模式可按不同通知类型设置渠道与接收人；
- 基础编辑模式可统一编辑一个产品下所有消息的渠道与接收人；
- 支持选择多个产品后批量编辑；
- 支持消息免打扰时间段和指定渠道；
- 影响业务停服的到期/欠费类消息不能设置免打扰。

这里体现了“产品 → 子消息 → 渠道 → 接收人”的四级结构，适合用在企业级通知偏好中心，不适合简化成一个全局开关。

### 9.4 接收人管理

消息接收管理公开文档说明：

- 接收人可以是主账号、子用户、协作者和专门的消息接收人；
- 消息接收人可以只用于收消息，不需要登录注册；
- 可按条件筛选接收人订阅的消息类型和产品历史消息；
- 支持产品订阅管理；
- 支持批量操作；
- 支持固定语音号码通知、夜间接收状态、闪信免打扰和营销消息免打扰。

这些能力进一步证明：通知中心不只是一张“事件表”，还包含收件人和渠道策略的运营面。

### 9.5 企业微信、机器人和安全边界

公开文档说明了微信、企业微信和企业微信群机器人等接收方式：

- 企业微信需要账号关联、子用户和应用可见范围满足条件；
- 群机器人使用 Webhook，支持测试推送；
- Webhook 地址只对创建者可见，文档明确要求不要向任何人透露；
- 事件触发器的 Bearer Token 用于请求校验，重新生成后旧 Token 立即失效；
- 删除事件触发器时，Webhook URL 和 Token 立即失效。

可复用的安全原则：

```text
通知状态可以公开给有权限的运营者，传输凭据、Webhook、Bearer Token、原始请求体不能进入通知列表、详情摘要、审计快照或浏览器日志。
```

## 10. 事件状态、通知状态和运营历史的归纳

以下表格分为“公开页面观察”和“Stage 22 可复用的规范化建议”，后者不是腾讯公开 API 声明。

| 对象 | 公开页面观察到的语义 | 本项目可规范化的 UI 状态 |
| --- | --- | --- |
| 站内信 | 未读、已读；可只看未读、批量标记已读、全部标记已读 | `unread` / `read`；读状态独立于业务事件状态 |
| 评测任务 | 已保存未运行、排队/运行中、暂停、继续、跑批完/评测完成、可报告/下载/标注 | `saved` / `queued` / `running` / `paused` / `completed` / `failed`；失败枚举需以后端事实为准 |
| 发布 | 待发布、后台发布流程、完成通知、唯一版本号、发布历史、版本还原、服务状态 | `pending_changes` / `publishing` / `published` / `failed` / `rolled_back_to_editing`；线上是否生效必须单独展示 |
| 触发器 | 启用/暂停；最近执行显示成功或失败；可立即运行 | `enabled` / `paused` + execution `succeeded` / `failed` |
| 运营数据 | 数据分析有约 10 分钟延迟；对话记录和不满意问题可筛选、查看、处理 | 数据集 `fresh` / `stale` / `unavailable`；处理动作单独记录 |
| 多渠道通知 | 渠道和接收人可配，部分关键消息有强制渠道要求 | 业务事件状态、渠道投递状态、读状态三层分开 |

推荐事件模型最少保留：

```text
event_id
 tenant_id / dataset_id / application_id
 event_type / event_subtype / severity
 occurred_at / received_at / read_at
 source_kind / source_id / source_revision
 status / channel_delivery_status
 safe_summary / action_target
 correlation_id / audit_reference
```

上述字段是本项目研究建议，不是从腾讯页面抄取的字段清单。`safe_summary` 应使用 allow-list，不能承载查询正文、结果正文、评论、工单、Token 或 Webhook。

## 11. 筛选、批处理和详情模式

### 11.1 可复用的筛选层级

结合消息中心、发布历史和应用运营页面，可以形成以下筛选优先级：

1. **时间**：接收时间、更新时间、执行时间；
2. **范围**：Tenant、Dataset/Knowledge Base、Application、Release/Channel；
3. **分类**：事件类型、子类型、来源、调用方式；
4. **状态**：未读/已读、成功/失败、排队/运行/暂停、待发布/已发布；
5. **搜索**：标题、资源名、版本号、事件 ID 的安全前缀。

筛选条应在桌面端保持一行或两行的明确层次，移动端转为“筛选”抽屉/底部面板，不把十几个选择器硬塞进横向滚动表格。

### 11.2 批处理的安全交互

公开页面中可验证的批处理包括：

- 消息部分标记已读/全部标记已读；
- 产品订阅批量编辑；
- 评测批量运行、下载、标注相关操作；
- 应用运营批量忽略、批量导出；
- 智能分类对符合筛选条件的未分类记录批量处理。

建议本项目的批处理统一采用：

```text
筛选条件摘要 → 当前选中数量 → 影响范围预览 → 二次确认（若有副作用） → 服务端结果摘要 → 可追溯审计
```

只读用户、无权限用户和 unavailable 状态下，批处理按钮应隐藏或真实 disabled，并展示原因；不能在浏览器假装完成。

### 11.3 详情面板

腾讯公开文档将“查看执行详情”“查看执行日志详情”“在应用运营中统一查看”分成不同层级。可复用的详情结构：

- Overview：标题、类型、状态、时间、来源、版本/修订号；
- Timeline/History：只展示服务端提供的事实时间线；
- Related resource：发布历史、评测任务、知识库、触发器或对话记录；
- Delivery/Read：读状态、各渠道状态、失败原因（安全摘要）；
- Actions：标记已读、打开来源、导出/下载、进入处理页面；
- Audit：操作者、系统事件、相关请求或运行 ID。

不要在详情中默认展开完整查询、完整模型输出、Webhook、Bearer Token 或用户上传的敏感文本。

## 12. TDesign 风格的可复用布局建议

> 本节是基于公开页面视觉和交互事实给出的本项目建议，不声称腾讯公开页面的所有内部实现都使用 TDesign。

### 12.1 桌面端

推荐使用企业控制台的固定骨架：

```text
GlobalHeader
 ├─ Product/Workspace navigation
 ├─ Global notification bell + unread Badge
 └─ Account / region / help

PageShell
 ├─ Aside: Release Center / Quality Operations / Notification Center
 ├─ Content: summary cards + filters + PrimaryTable
 └─ Optional right rail: status horizon / current scope / freshness
```

可优先使用 TDesign 的语义组件：

- `Layout` / `Header` / `Aside` / `Content`：保持产品级骨架；
- `Badge`：只显示服务端未读数，不能前端累加伪造；
- `Tabs`：区分全部、未读、发布、评测、质量和系统事件；
- `PrimaryTable`：桌面端事件历史和批处理；
- `Tag` / `Status` / `Progress`：状态、严重性和进度分开表达；
- `Dropdown` / `DateRangePicker` / `Select`：筛选；
- `Drawer` / `Dialog` / `Timeline` / `Steps`：详情、确认、历史和执行阶段；
- `Alert` / `Empty` / `Result` / `Skeleton`：错误、空态、完成态和加载态；
- `Tooltip` / `Popover`：解释延迟、权限、渠道和不可用原因。

### 12.2 移动端

- 保留顶部全局通知入口，但把主导航折叠到菜单；
- 事件表转换为单列事件卡片，显示类型、状态、时间、来源和一个主要 CTA；
- 筛选放入全屏/底部抽屉，提交后展示筛选摘要；
- 详情使用全屏 Drawer/页面，而不是把桌面宽表强行压缩；
- 批处理保持悬浮/底部操作栏，显示已选数量和影响范围；
- 详情关闭后恢复原始焦点；
- 375px 和 280px 下不能因为 Badge、表头或按钮出现水平溢出。

### 12.3 视觉取舍

公开腾讯页面普遍使用克制的蓝色主操作、浅灰边框/表头、密集但清晰的表格、绿/橙/红状态点和大量留白。可以采用类似的企业信息密度，但不要复制腾讯云 logo、字体声明、截图、产品名、精确布局或品牌插图。Uiverse/Morphicons 只能作为缺少的非核心装饰补充，不能替代通知 Badge、Table、Drawer、Dialog、权限/状态控件。

## 13. Empty / error / read-only：已验证边界与本项目要求

### 13.1 本轮直接验证到的边界

- 公开文档可以看到功能说明和静态截图；
- 实时 ADP 控制台和实时消息中心都需要登录；
- 未登录请求消息中心最终到 `https://cloud.tencent.com/login?s_url=...`；
- 未登录请求 ADP 控制台同样到腾讯云登录页；
- 因没有账号态，本轮没有对真实“无通知”“无权限”“列表加载失败”“部分渠道失败”“只读详情”做伪造观察。

### 13.2 对本项目的明确建议

必须区分以下状态，而不是都渲染成空白表格：

```text
empty       = 已授权且查询成功，但当前范围没有事件
partial     = 已授权，但部分来源/渠道不可用
error       = 查询或 mutation 明确失败
unavailable = 未满足能力/认证/依赖条件，不能确认数据为空
read-only   = 可读取事实，但没有 mutation 权限
stale       = 有数据，但数据新鲜度已超过定义阈值
```

每个状态都应展示原因、最近更新时间和可执行的下一步。尤其是未登录或无权限时，不应返回 `[]` 并显示“暂无通知”；这会把安全拒绝伪装成业务空态。

## 14. 不可复制边界

| 边界 | 不能做的事 | 本项目应怎么做 |
| --- | --- | --- |
| 认证边界 | 不得绕过腾讯云登录访问真实消息/应用数据；不得自动扫码或复用账号态 | 只研究公开文档；本项目使用自身认证、Tenant ACL 和 read-only projection。 |
| 数据真实性 | 不得把公开截图里的未读数、任务数、版本号当成实时数据 | 所有 Badge、计数、完成状态从服务端权威事实生成；没有事实就显示 unavailable。 |
| 品牌与版权 | 不复制腾讯云 logo、产品截图、页面源码、精确文案、内部 DOM/selector 或品牌图形 | 只借鉴信息架构、状态语义、密度和交互模式；使用本项目自己的品牌和 TDesign theme。 |
| 凭据安全 | 不把 Webhook URL、Bearer Token、AccessKey、原始请求体写入通知或审计 | 使用 allow-list 摘要、脱敏引用和不可逆 digest；敏感字段读时 fail closed。 |
| 副作用 | 不因“发布完成通知”自动触发回滚、重试、发布、标记已读、外部推送 | 通知 CTA 只进入受权限保护的详情/确认流程；mutation 需要服务端幂等和审计。 |
| 事件语义 | 不用颜色或文案猜测执行成功；不把通知发送成功等同于业务完成 | 分离业务事件状态、渠道投递状态、读状态和审计状态。 |
| 范围隔离 | 不允许跨 Tenant/Dataset 读取或批处理 | 所有列表、详情、批处理和关联跳转都携带服务端校验的作用域。 |
| 任务历史 | 不把一条通知当作完整发布/评测历史 | 通知关联发布历史、评测任务、执行日志和版本/修订事实。 |
| 移动端 | 不照搬桌面宽表导致溢出，也不通过截断关键信息隐藏状态 | 移动端使用卡片/抽屉/底部筛选，保持可读性和键盘/触控可达性。 |
| 文档时效 | 不假设公开文档示例永远代表当前控制台实现 | 记录检索日期和页面最近更新时间；上线前以自身后端契约和真实受控环境复核。 |

## 15. 推荐的 Stage 22 产品方向（仍为研究结论，不是实现任务）

如果后续进入实现，建议将 Stage 22 命名为 **Notification & Operations Center**，并保持与 Stage 21 Quality Operations 的并列关系：

```text
Release Center | Quality Operations | Notification Center
```

核心工作区建议：

1. **全局入口**：Header `Bell` + 服务端 unread Badge；Badge 点击进入 Notification Center，而不是仅打开一个临时 Popover。
2. **通知列表**：All / Unread / Release / Evaluation / Quality / System；支持接收时间、类型、子类型、来源、状态和安全标题筛选。
3. **事件行**：未读强调、状态 Tag、来源图标、发生时间、更新时间、作用域、一个主要 CTA；不要在行内展示原始 payload。
4. **详情 Drawer**：Overview、Timeline、Related Operation、Delivery/Read、Audit；详情只接收服务端安全投影。
5. **批处理**：批量标记已读、批量归档/隐藏（如果业务需要）和批量打开来源；所有操作显示选中数量、作用域和结果。
6. **完成通知**：发布、评测下载、再认证等异步完成事件使用统一事件契约；通知只做“完成事实 + 安全摘要 + 跳转”，不重新实现业务状态机。
7. **运营历史**：发布历史、评测报告、扫描 Run、Alert、Recertification Job 是可追溯的关联资源；通知详情不能成为唯一历史来源。
8. **状态门禁**：empty/error/unavailable/read-only/partial/stale 分开；任何不确定状态都 fail closed。
9. **移动端**：375px/280px 使用风险卡片和全屏详情，筛选/批处理走抽屉和底部栏，保持无水平溢出。

## 17. 最终研究结论

腾讯云公开页面提供了一套成熟的企业级通知/运营范式：

```text
Global entry
  → unread-aware inbox
  → time/type/source filters
  → batch operations
  → detail drawer/log/history
  → related business object
  → auditable completion fact
  → multi-channel preference and delivery policy
```

对 RAG4C 最有价值的不是复制腾讯页面，而是把该范式与已有 Stage 20/21 的 Release Quality、SLO、Alert、Recertification authority 结合：

- 通知是跨模块的安全索引；
- 发布/评测/扫描/再认证仍由各自权威服务负责；
- 全局未读数必须由 Tenant-safe 服务端事实产生；
- 详情只展示 allow-list、revision、时间、状态和关联 ID；
- 失败、过期、不可用、只读和空态必须显式区分；
- 移动端不牺牲状态和操作可达性；
- 不伪造腾讯控制台当前数据，也不复制腾讯品牌资产。

**Stage 22 本轮到此收束；没有实现代码，没有登录，没有外部副作用。**

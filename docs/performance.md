# 并发性能 / 可用性 / 稳定性

本文记录 RAG4C 服务端的性能基线、已修复的缺陷，以及复现方法。
数字全部来自 `scripts/bench/`，可复现；每条改动都附「为什么」而不只是「改了什么」。

## 1. 怎么测的

真实上游（硅基流动 / Milvus）的延迟方差有几百毫秒，会把被测信号完全淹没，
所以压测打的是本地模拟上游 `scripts/bench/mock_upstream.py`（固定 ~100ms 延迟、
确定性向量）。**这意味着测的是服务端并发能力，不是答案质量**——模拟嵌入
是哈希出来的，召回结果毫无意义。

```bash
# 1) 起模拟上游
python scripts/bench/mock_upstream.py --port 8899

# 2) 起被测服务（指向模拟上游的配置）
RAG4C_ENV_FILE=config/.env.bench python -m uvicorn server.app:app --port 8010

# 3) 压测
python scripts/bench/load_query.py --url http://127.0.0.1:8010 \
    --concurrency 32 --total 96 --pattern mixed --out output/bench/x.json
```

三种负载各回答一个不同的问题：

| 负载 | 含义 | 测什么 |
|---|---|---|
| `distinct` | 每个请求问不同问题 | 全部 miss 缓存，真实吞吐上限 |
| `hotspot` | 所有请求问同一个问题 | 缓存击穿路径会不会把服务掐死 |
| `mixed` | 八成热点两成长尾 | 最接近真实流量形态 |

### 两个测量陷阱（都真踩过）

1. **不做缓存隔离，测的是缓存不是链路。** 第一版问题集只有 8 条而总量 96，
   第 9 个请求起全是缓存命中，测出 P50 1073ms / 119 QPS，两个数字都漂亮也都
   毫无意义。现按「每轮一个 nonce」隔离：同轮内 hotspot 仍撞同一个 key（这是
   它要压的东西），只与上一轮隔离。
2. **冷启动会被误读成性能退化。** 重启后第一轮 distinct 测出 7.49 QPS，紧接着
   连测三轮 18~22 QPS——差的不是代码，是惰性建客户端 / 连接池的一次性开销。
   现默认 `--warmup 4`。

### 一个必须说明的边界

模拟上游自身的并发吞吐上限约 **40~60 req/s**（ThreadingHTTPServer + GIL），
而一次 `distinct` 问答要打约 6 次上游。**所以 distinct 的绝对 QPS 是被压测
工装卡住的，不代表 RAG4C 的上限。** distinct 一栏里可信的是成功率与错误分布，
不是 QPS 绝对值；hotspot / mixed 走缓存与合并路径、不打满上游，QPS 才有意义。

## 2. 基线与结果

并发 32 / 总量 96 / 模拟上游。

| 负载 | 改前 | 改后 |
|---|---|---|
| distinct | 20/96（20.8%），76×429，7.44 QPS，P95 2563ms | **96/96（100%）**，0×429，P95 ~4500ms |
| hotspot | 27/96（28.1%），69×429，36.40 QPS，P95 696ms | **96/96（100%）**，0×429，**105~131 QPS**，P95 ~500ms |
| mixed | 20/96（20.8%），76×429，17.79 QPS，P95 1111ms | **96/96（100%）**，0×429，**35~53 QPS**，P95 ~800ms |

改前近八成请求被 429 拒掉。**成功率 20.8% → 100% 是这轮最实在的收益**，
且与压测工装的吞吐上限无关。

压力上探（改后，distinct）：并发 64 → 23.52 QPS / P95 2863ms / 100%；
并发 128 → 22.50 QPS / P95 5819ms / 100%。吞吐平台化、延迟线性增长、零错误
——这是过载时该有的形状（Little's law），而不是改前那样成片 429。

### 接入 Redis 之后的复测（⑬⑭ 落地后）

并发 32 / 总量 96 / 模拟上游，每档取三轮中位数（单轮方差很大，hotspot
实测在 161~234 QPS 之间跳，只看一轮会得出任意想要的结论）：

| 负载 | Redis 关 | Redis 开 | 差异 |
|---|---|---|---|
| distinct | 121.4 QPS | 115.6 QPS | **−5%** |
| hotspot | 226.3 QPS | 225.8 QPS | 持平 |
| mixed | ~196 QPS | 183.2 QPS | 略降，在方差内 |

全部 96/96 成功、零 429/503。distinct 那 5% 是**应该付的**：这一档 100%
未命中，每个请求都白跑一遍 L2 查询 + 抢锁 + 回写的往返，却没有任何命中
可拿。换来的是多副本下的跨进程共享，单进程压测天然照不出这份收益。

**单进程压测测不出 L2，这是工装的结构性限制，不是缓存没生效。**
``load_query.py`` 给每一轮压测的问句都拼了一个 nonce（每轮一个，见该文件
开头的陷阱说明），就是为了让每轮从冷缓存起跑——于是第二个副本永远不可能
命中上一轮写进 L2 的键。实测到的 ``l2_hits: 0`` 是这个设计的必然结果。

跨副本收益改用定向验证：起 A(8010) / B(8011) 两个副本共用同一个 Redis，
向 A 问一句全新的问题，再把同一句问给 L1 全冷的 B——B 的
``l2_hits: 1 / promotions: 1``，答案直接由 L2 供出，没有重跑检索与生成。
这才是 L2 存在的理由，也是它唯一能被观测到的地方。

另有一处测量陷阱值得记：重启前的那次复测得出 distinct 74.5 / mixed 92.0，
看着像大幅退化。实际上 8010 上跑的是**几小时前启动的旧进程**，测的根本不是
当前代码；用当前代码重启后是 121.4 / 226.3 / ~196，反而高于基线。压测之前
先确认被测进程的代码版本，否则量到的是进程年龄不是代码质量。

## 3. 已修复的缺陷

### ① 观察者注册泄漏 → O(n²) 衰减【最严重】

**症状**：服务越跑越慢且不自愈，只有重启能恢复。连续压测 distinct：
21.8 → 8.4 → 7.4 → 6.6 → 6.1 QPS，单调下滑。

**根因**：`core/observability.py` 里 span→metrics 的回调是个**闭包**，而
`register_span_observer` 的去重是 `if fn not in _span_observers`——闭包每次
都是新函数对象，身份永不相等，去重形同虚设。偏偏 `rag.answer_query` **每次
问答都调一遍** `setup_observability`（rag.py:502，注释还写着"幂等"）。于是
观察者列表每问一次长一个，第 N 次问答的每个 span 要回调 N 个观察者。

实测 920 次问答后，9 个阶段共记录 43 万条指标——放大约 **473 倍**
（≈ 920 × 平均 460 个观察者，与半数增长的理论值精确吻合）。

**修复**：回调改为模块级函数，身份恒定，去重真正生效（注册 6 次 → 1 个观察者）。
另在 `core/tracing.py` 加了泄漏告警：观察者数达 32 时打一条带 `__qualname__`
的 warning——这类泄漏不报错、只让服务慢慢窒息，宁可吵一点也别让它安静地死。
回归断言见 `smoke_resilience.py` (l2)：`setup_observability` 调 6 次后
span 仍只记 1 条。

**验证**：`span/query` 比值 473 → **1.0**；连测 6 轮 mixed 稳定在
44/53/50/35/47/43 QPS，无下滑趋势。

### ② 并发上限按 CPU 核数设置（4）

这条链路**不是 CPU 密集**：一次问答约 5.6 秒，绝大部分在等 Milvus / 嵌入 /
重排 / LLM，全在 GIL 之外阻塞。按 4 并发算吞吐天花板 ≈ 4/5.6 ≈ 0.7 QPS。
改为 `RAG4C_QUERY_MAX_CONCURRENT=32`、`RAG4C_QUERY_QUEUE_MAX=128`。

### ③ single-flight 造成队头阻塞

原来的合并只有线程层一份，位置在 `_run_query` **内部**——等待者必须先抢到
信号量槽、再占住一个工作线程，然后才在 `Event.wait()` 上睡觉。后果是**一个
热点问题就能把整个服务掐死**：32 个槽全被等待者占着，其它请求一律 429。

改为在事件循环层加在途登记表（`_aio_flights`），合并发生在**抢槽之前**，
等待者不占槽也不占线程。摘登记时核对身份，避免删掉下一轮的登记。
hotspot 从 36 QPS / 28% 成功率变成 105~131 QPS / 100%。

### ④ 重试 × 超时预算自相矛盾

LLM 单次 timeout=120s、max_attempts=3，最坏 120×3 + 退避 ≈ **361 秒**，而 HTTP
总闸只有 240 秒。上游一超时，工作线程必然在客户端早已放弃之后继续空转两分钟
——过载时正是这部分负载把服务拖垮。

加了请求级截止时间（`core/retry.py` 的 `deadline`），用 **thread-local** 而非
contextvars：整条链路是同步代码、跑在 `run_in_executor` 的单个线程里，
thread-local 天然贴合，且**不需要改那 14 个调用点**——在线程入口设一次，
底下所有 `retry_call` 自动受约束。重试前检查「睡完还剩不剩得下一次尝试」，
不够就直接放弃并计入 `total_deadline_aborts`（与 `total_failures` 分开计：
失败多说明上游有问题，放弃多说明超时预算配小了）。

### ⑤ 嵌入 / 重排零重试

两者与 LLM 打的是同一类端点、面对同样的瞬态失败，却一个有重试一个没有。
重排更糟：它的失败被 `retrieval/pipeline.py` 静默吞掉降级为"不重排"，
表现是「检索质量突然变差，但日志里一切正常」——最难查的那类故障。
两处都补了 `retry_call`。

### ⑥ 同一次问答重复嵌入同一段文本

路由器嵌一次 `search_query` 决定走哪条路，主检索紧接着又嵌同一个字符串，
两次远程往返拿回完全相同的向量。改为在 `ApiEmbedder.embed_query` 上加实例级
LRU（512 条）。

没有选「把路由器算出的向量传下去」这个更省事的方案：那要求两处对「嵌的到底是
哪个字符串」保持一致（hyde 开启时检索层嵌的是假设文档，不是查询），一旦哪天
有人改了其中一处，传下去的就是个**错的向量**，不报错，只让召回悄悄变差。
按内容做键天然没有这个问题。缓存挂在实例上而非模块级，配置热更新换模型时
自然换缓存，不会拿旧模型的向量去查新模型建的索引。

### ⑦ `/api/graph/search` 完全没有并发保护

加了独立闸门 `GRAPH_MAX_CONCURRENT=8` / `GRAPH_TIMEOUT_S=30`，非阻塞抢占失败
即 429。与问答闸门分开，避免图检索把问答的槽吃光。

### ⑧ 缺存活 / 就绪探针

原来只有 `/api/health`，而它会真连 Milvus（2 秒超时）。拿它当 liveness 探针
意味着「Milvus 挂了 → 探针失败 → 编排器重启本服务」，而重启一个健康的进程
既治不好 Milvus，又把仅存的降级能力弄没了。**存活问的是"要不要重启我"，
就绪问的是"要不要给我发流量"，依赖故障时两者答案相反。**

- `GET /livez` — 纯进程存活，不碰任何外部依赖
- `GET /readyz` — 反映 `probe_components()`；degraded 仍返回 200（Milvus 挂了
  但 LLM 还在时能给出诚实的"资料暂不可用"，比被摘出负载均衡更好），只有
  down 才 503；**队列打满也算不就绪**，让流量导去别的实例，即背压向上传导

### ⑨ 重排降级是**静默**的

重排失败（分数条数对不上 / `RerankError`）只往 `traces` 里追一行就算完：
服务照样 200，日志一片干净，唯一的外部症状是「检索质量莫名其妙变差了」——
而这恰恰是最难被归因的一类故障。降级本身是对的，错的是降级得无声无息，
连带的后果是熔断器永远等不到失败信号。

新增 `_report_rerank_degraded()`，两条失败路径都走它：计数
`retrieval.rerank.degraded` + 一条 WARNING 日志。

### ⑩ 请求体无上限

Pydantic 的 `max_length` 是在**读完整个 body 并解析成对象之后**才校验的。
一个 500MB 的请求哪怕最终必然因 query 超长被拒，服务端也已经先把这 500MB
读进了内存——校验拦得住脏数据，拦不住资源耗尽。

新增 `limit_body_size` 中间件，按 `Content-Length` 超过 1 MiB 直接 413。

中间件的**注册顺序**在这里是有意义的：Starlette 的 http 中间件是后注册者
更靠外（实测确认，不是凭印象——我一开始的判断正好反了）。access_log 要能
记录到被 413 拒掉的请求，就必须包在闸门外面，因此它得**后**注册。写反了
的直接后果是被拒流量完全不进访问日志，而这类流量恰恰是最该被看见的。

### ⑪ 重排器没有熔断：降级了正确性，没降级延迟

⑨ 之后重排失败会如实上报，但**每个请求仍要付满超时 × 重试才轮到降级**。
重排器（SiliconFlow 远程服务）真挂掉时，并发上来后线程全卡在一个已知挂掉
的下游上——结果早已注定是"用召回顺序"，代价却一分不少地付了。

`RetrievalPipeline` 新增可选 `reranker_cb`，在 `rag.py` 与既有两个熔断器
一起装配（`CircuitBreaker.__init__` 自动注册进全局表，`/api/health` 和监控页
因此能一并看到 `reranker` 的状态）。打开后直接跳过重排，仍走
`_report_rerank_degraded` 上报，trace 里写明「熔断打开」而非静默。
不传 `reranker_cb` 时行为与接入前完全一致。

回归覆盖在 `smoke_retrieval.py` 的 (e2)：连续 2 次失败后熔断打开、**重排器
调用次数不再增长**、trace 说明原因、结果仍是完整的召回顺序。

### ⑫ 重排的 `requests` 兜底路径非线程安全

`ApiReranker` 是**进程级单例**（挂在 `get_pipeline()` 缓存的组件图上），最多
32 个工作线程同时调用。`httpx.Client` 声明了线程安全，`requests.Session`
明确声明**不是**——它的 `HTTPAdapter` 连接池与 cookie jar 在并发下会被写坏。
原代码两条分支都存进同一个 `self._client`，于是只要环境里没装 httpx，
32 个线程就共用一个 Session。

这个 bug 的隐蔽之处在于它**永远不会以自己的面目出现**：连接复用错乱表现为
偶发的传输层异常，而重排失败会被降级成"不重排"，最终只剩「检索质量偶尔
变差」这种查不动的症状。

改为 httpx 仍全进程共享（它本就线程安全），requests 走 `threading.local()`
每线程一个。没有选「加锁串行化」：那会把重排变成全局瓶颈，为一条兜底路径
牺牲主链路并发，代价方向反了。

验证时踩了个测量陷阱：4 个线程只测出 3 个不同的 `id()`，看着像仍有共享。
实际是线程退出后 thread-local 释放、Session 被回收，后来的对象复用了同一个
内存地址——`id()` 在对象生命周期不重叠时本就可以相等。持有强引用后重测，
4 线程 4 个 Session。

### ⑬ 答案缓存与 single-flight 只活在单进程内存里

**背景**：③ 把 single-flight 挪到了事件循环层，但缓存本身（`server/app.py`
的 `_query_cache` / `_query_flights`）仍是两个模块级 dict。单副本下够用，
一开多副本就露馅：N 个副本各存各的，命中率被切成 1/N；而热点问题（发布会
当天所有人问同一句）会**同时打穿 N 条完整 RAG 链路**——一次约 5.6 秒，还要
烧掉一整轮 token。

改为 `core/query_cache.py` 的两级缓存，语义与被替换的 `_cache_*` 一一对应：

    读：L1 -> L2 -> miss          写：L1 + L2 同写
    在途：进程内 Event + Redis SET NX 锁（跨进程合并）

L1 是进程内 TTL + LRU，L2 是 Redis String。两级的 TTL 分开配（默认 600s /
900s）不是疏忽：L1 是本进程几十条的临时件，短 TTL 换新鲜度；L2 是跨副本共享
的公共品，多存一会儿才摊得平那次全链路的成本。绑成同一个值只会逼人在
「本地太陈旧」和「共享太浪费」之间二选一。

**前提：Redis 是加速件，不是依赖件。** 缓存有等价的进程内实现（LRU），
排队也有（`asyncio.Semaphore`）。所以 `core/redis_client.py` 的每个出口都
遵守同一条契约——**连不上 / 命令失败一律返回 None 或 False，绝不抛给调用方**
——`core/query_cache.py` 和 `core/queue_stream.py` 的所有公开 API 一个异常
都不往外漏。Redis 缺席时，缓存的行为与搬家前的纯 L1 实现逐字节一致，排队原样
退回进程内信号量。反过来做——Redis 一挂问答跟着 500——是为一个**可选**组件
搭上整个服务的可用性，方向反了。首次不可用记一条 WARNING 之后静默：Redis
挂着的那段时间里每个请求刷一行日志，只会把真正有用的错误淹掉。

**为什么锁释放必须用 Lua 做比较删除。** `GET` 看到令牌是自己的、再 `DEL`，
这两条命令之间有个窗口：窗口里锁可能已经过期、并被**另一个进程**重新持有，
这时 `DEL` 删掉的是别人的锁。此后两个进程同时以为自己是 owner，热点问题一次
打穿两条链路。要命的是这个竞态**只在一次查询耗时超过 `lock_ttl_s` 时才复现**
——也就是系统最忙的时候；压测压不出来，线上专挑最坏的时刻发作。Lua 在 Redis
里是单线程原子执行的，这才是 GET-then-DEL 的唯一正确写法。

**为什么抢到锁之后要再查一次 L2。** 等待者不是随机时刻拿到锁的，它恰恰是在
「赢家释放锁」的那一瞬间抢到的——而那一刻答案早已写进 L2。不复查就会把刚算完
的东西原样重算一遍：single-flight 只挡住了并发窗口，挡不住紧随其后的那一批，
在热点键上约等于完全没生效。所以 `_reserve_across_processes` 的第二轮起，
拿到锁的第一件事是重查 L2，命中就立刻还锁走人。

**为什么 query_cache 不复用 `redis_client.call()`。** 那个统一容错出口把
「命令失败」和「键不存在」都塌缩成 `None`，对绝大多数命令没问题，对 `SET NX`
是致命的：返回 None 既可能是「别人持锁，我该等」，也可能是「Redis 挂了，我该
立刻自己算」。混为一谈的后果是 Redis 一挂，每个请求都要白等一个
`wait_timeout_s` 才开始干活，缓存从加速件变成刹车片。所以 query_cache 自带
一个返回 `(ok, value)` 的 `_exec()`，把这两种情况分开。

**为什么 `_digest()` 用完整 sha256、不截断。** 截到 16 字符省下的那点内存，
换来的是生日碰撞——两个不同问句共用一条缓存，表现为「偶尔答非所问」。这类
bug 在线上几乎不可能被定位，而省下的内存以字节计。另外键名取哈希而非问句本身
也是必须的：键名会出现在 `MONITOR` / `SLOWLOG` / `KEYS *` / RDB 里，等于把用户
问句泄漏给任何能连这个 db 的人。L1 反而直接用逻辑键做索引——它只活在本进程
内存里，而本进程本来就持有原始问句，再哈希一遍纯属自欺。

**键前缀 `rag4c:` 是硬要求，不是整洁癖。** 目标实例与其它应用共用同一个 db
（实测 `dbsize=19`），没有前缀就是在别人的键空间里裸奔。与之配套的一条纪律：
**仓库里不存在任何针对生产前缀的批量删除入口**，没有 FLUSHDB，也没有对
`rag4c:` 的 `SCAN`+`DEL`。L2 全都带 TTL，等它自己过期是唯一不需要祈祷的方案；
`clear_l1()` 因此只清 L1。

**一次真出过的事故：测试数据写进了生产缓存命名空间。** `smoke_server` 走的是
`server/app.py` 的真实缓存路径，键前缀取自配置，于是一次开着 `RAG4C_REDIS_URL`
的测试跑完，共用实例的生产命名空间里多出了这么一条：问句「测试问题」、答案空
串、`abstained: true`。「测试问题」是一句**完全可能被真人输入**的中文，而缓存
不看来路只看键——15 分钟 TTL 内真有人问同一句，拿到的就是这条桩数据。这不是
「不整洁」，是测试污染线上应答。

修的方向是**在测试侧强制隔离**，而不是靠「记得起一个唯一的问句」——那种约定
迟早有人忘，而忘掉的代价落在真实用户身上。新增 `scripts/_smoke_redis.py`：
`run_tests.py` 在运行器这一层为整轮测试统一下发 `rag4c-test:run:` 前缀（放在
运行器而不是各脚本，是为了让**将来新增的**冒烟脚本自动获得隔离），收尾兜底
扫一次；脚本单跑时自己调 `isolate_redis_keyspace()` 切前缀并注册 atexit 清理。
`sweep()` 是仓库里唯一的批量删除入口，因此它**拒绝任何不以 `rag4c-test:`
开头的前缀**——这不是防御性冗余，误传一个 `rag4c:`（或空串）就会清掉共用实例
上别人的真实数据，代价不可逆；扫描用 `scan_iter` 而非 `KEYS`，后者会把共用
实例整个阻塞住。注意隔离必须在 `import server.app` **之前**做完：配置是
`lru_cache` 单例，第一次 `get_settings()` 之后再改环境变量就晚了。

**两个由服务层决定、而不是让缓存自己猜的参数。**

- `_build_query_cache()` 里 `wait_timeout_s = QUERY_TIMEOUT_S * 0.9`。缓存的
  默认等待时限对齐锁 TTL（300s），而 HTTP 总闸是 240s——照默认值走，客户端
  240 秒就放弃了，工作线程还在为一个**没人接收的答案**继续排队到 300 秒。这
  正是 ④ 那条 deadline 要根除的空转。谁知道自己的总闸是多少，谁就该把这个数
  传进去，所以由服务层构造 config 再 `install_query_cache()`。
- `_cache_peek()` 用 `allow_l2=False`。这个函数在**事件循环里**被调用，而查
  L2 是一次网络往返、`socket_timeout` 是 1 秒。Redis 一卡，每个请求都能把整个
  事件循环拽停最长 1 秒。跨副本命中并没有丢，只是推迟到 `_run_query` 里的
  `reserve()` 才发生——代价是 L2 命中要多占一个执行槽，但只占一次 GET 的毫秒
  级时间，与「占着槽跑完一整条 RAG 链路」完全不是一回事。

### ⑭ 准入控制也只有进程内视图：Redis Streams 队列

进程内的 `asyncio.Semaphore(32)` + `_pending` 计数在**单副本**下已经是完备的
准入控制，这时上 Redis 纯属多余——多一次往返、多一个可挂的组件。所以
`queue_backend` 默认 `memory`，`core/queue_stream.py` 整体关闭。

它挣钱的场景只有一个：**多副本**。这时 N 个副本各管各的信号量，"32 并发"这个
数字失去意义（实际是 N×32 打向同一套 Milvus / 嵌入 / LLM 配额），`/readyz`
报出来的 pending 也只是本副本的局部视图。换 Streams 后并发是全局的、深度是
集群级真值。选 Streams 而不是 `LPUSH`/`BRPOP` 的**唯一硬理由**是崩溃恢复：
`BRPOP` 一弹出，任务就只存在于那个进程的内存里，被 OOM kill 就连同它的等待方
一起蒸发；Streams 把「已投递未确认」显式建模成 PEL，别的副本用 `XAUTOCLAIM`
接手。代价也要认：热路径上多几十毫秒。一次问答 5.6 秒，可以忽略；哪天链路变成
50ms 级，这个队列就该拆掉。

**`XACK` 不减少 `XLEN`——这是 Streams 最容易踩空的地方。** `XACK` 只把条目从
PEL 摘掉，条目本身仍留在流里、仍计入 `XLEN`。不配 `XDEL` 的话，`XLEN` 表示的
是「历史累计提交总数」而不是队列深度，于是基于深度的背压会在服务累计处理满
`queue_max` 次请求之后**永久返回 429**——一个只跟运行时长有关、跟当前负载
完全无关的故障。正确的不变式是：

    XLEN = 排队中 + 处理中
    排队中 = XLEN − XPENDING.pending

`complete()` 因此固定走「写结果 -> `XACK` -> `XDEL`」，`stats()` 的
`queued` 由这个减法算出来。

**顺序是先写结果、再 XACK，不能反。** 两步之间崩溃时：现在这个顺序下任务还在
PEL 里，会被 `XAUTOCLAIM` 重做一遍（等待方早已取走结果并删了键，重做的结果无人
认领，靠 TTL 自灭）——多算一次，但不丢；反过来先 `XACK`，任务从 PEL 消失而结果
没写成，等待方只能干等到超时——丢任务。**宁可重做，不可丢。** 同理
`consume_once()` 是**先 reclaim 再 fetch**：反过来的话只要新任务源源不断，孤儿
任务就永远排在后面饿死，恢复能力形同虚设。`min_idle_ms` 默认 5 分钟（查询总闸
240s 再留一倍余量），宁大勿小——设小于任务最坏耗时就会把活人手里的任务抢走
并发重做。

**`socket_timeout_s = 1.0` 约束了所有阻塞调用。** 这条约束是全局的，很容易在
写消费端时忘掉：`XREADGROUP BLOCK 5000` 发在一个 socket 超时 1 秒的连接上，
服务端还在老实阻塞等消息，客户端已经先超时抛 `TimeoutError` 了——外部症状是
「worker 一直报错，但 Redis 一切正常」。所以 `_safe_block_ms()` 把 BLOCK 统一
压到 socket 超时的 80%，留出往返余量。同一条约束也决定了**单个 job 的结果回传
用轮询**（10ms 起、指数退避到 200ms），而不是：

- **Pub/Sub**——worker 可能在等待方 SUBSCRIBE 完成之前就把结果发了，消息直接
  丢失，还得再补一次 GET 兜底，两套机制复杂度翻倍；
- **per-job 流 + `XREAD BLOCK`**——长 BLOCK 先被客户端超时打断，最终还是退化成
  轮询，而且每个任务留一个流对象要显式删，String 的 TTL 自己会过期。

轮询的真正成本是空转的 GET，退避就是为了压住它；一次问答 5.6 秒，多等这点
可忽略。`MAXLEN` 近似裁剪（10000）是**兜底不是准入**：`queue_max`（128）远
小于它，正常情况轮不到裁剪出手，它防的是「消费者全挂 + 生产者不看深度」把
内存吃光。等待超时时生产者会尽力 `XDEL` 撤单——「排到最后终于被执行、但客户端
早就走了」的活是纯浪费。

### ⑮ 缓存只会过期，不会失效

**症状（未发生的事故，但差一点）。** ⑬ 把答案缓存做成了跨副本共享，TTL 15
分钟。于是一条链路成立了：用户提问 → 语料里没有 → 系统弃权（"资料里没有
相关内容"）→ 这个"没有"被写进 L2 → 用户意识到少了份文档，上传 → 入库成功
→ 用户满怀期待地再问一次 → **系统在接下来的 15 分钟里继续说"资料里没有"**。

排查 `QueryCache.invalidate()` / `clear_l1()` / `reset_query_cache()` 的调用
方，生产代码里**一处都没有**——尽管 `invalidate()` 的文档字符串写着"配置变更
/ 重建索引后调用"。`/api/config/update` 更直接：它能热换 embedding 模型，换完
之后旧答案是用**上一套检索**算出来的，却什么都没失效。

**为什么不能靠删键。** L2 的键名是 `sha256(逻辑键)`（`core/query_cache.py`
的 `_digest`），不可逆：拿着 `tenant=acme` 反推不出它写过哪些键。按前缀扫也
不行，键名里没有租户信息——这是故意的，问句和租户不该以明文躺在 MONITOR /
SLOWLOG / RDB 里。何况目标 Redis 与别的应用共用一个 db，仓库里不存在、将来
也不该有任何针对生产前缀的批量删除入口。

**做法：把代次号拌进缓存键**（`core/cache_epoch.py`）。缓存键末尾多一段
`<全局代次>.<租户代次>`，语料一变就 `INCR` 对应的代次。代次一涨，所有旧键在
逻辑上**再也拼不出来**，它们变成无人引用的垃圾，由各自的 TTL 自然回收。O(1)
失效，不扫键、不删键、不碰别人的键空间。

粒度定在**租户**而不是知识库，有两个各自独立成立的理由：

1. `dataset_id=""` 的语义是"不限知识库、全域检索"，它的答案覆盖该租户下所有
   知识库——往任何一个库写入都必须让这批缓存失效；
2. 图索引里根本没有 `dataset_id` 字段（`core/graph_store.py` 全文 0 处），
   图检索只按租户隔离。开着 `graph_index_on` 时，任一库的入库都会改变同租户
   下所有库的图检索结果。

代价是同租户跨库的过度失效。入库是分钟级低频操作，多算几次远比发出过期答案
便宜。

已接上的触发点：文档入库完成（`indexing/state_machine.py`）、增量重建
（`indexing/reindex.py`）、源同步真的写了东西（`sources/runner.py`）、
`--reset` 清空知识库（`scripts/ingest_source.py`）、配置热更新与集合重建走
全域 `bump_all`（`server/app.py`、`scripts/rebuild_collection.py`）。

**这里最容易踩的坑，我自己先踩了一遍：口径不一致。** 写侧的租户来自
`catalog`，存的是请求原样传进来的值，可能是 `""`；读侧的缓存键用的是
`resolve_tenant` 解析后的值，强制隔离下 `""` → `"default"`。同一个租户，代次
却记在两个格子里——入库照常涨代次，查询照常命中旧缓存，**失效彻底失灵而且
一声不吭**。修法不是在每个调用点加一句 resolve，而是把归一化放进
`cache_epoch._norm()` 这唯一入口：调用方想错也错不了。同样的理由，
`server/app.py` 的 `_cache_key()` 也改成先 `resolve_tenant` 再进键。

**降级契约（与 Redis 有关的一切一致）：代次是加速件不是依赖件。** 读不到就
**沿用上次读到的值**，绝不因为读失败去换一个新代次——后者会让 Redis 每抖一下
就全量击穿缓存，为了一个可选组件的抖动把整片流量打到 LLM 上。Redis 缺席时
退回进程内计数器，单副本部署下失效照常生效。

**而且代次读从不阻塞。** 拼缓存键发生在事件循环里，而 Redis 的
`socket_timeout` 是 1 秒——⑬ 里 `_cache_peek` 刻意不查 L2 就是为了躲开
"Redis 一卡，每个请求把事件循环拽停 1 秒"，代次读要是又把它请回来等于白躲。
所以 `current()` 走 stale-while-revalidate：进程内缓存 3 秒，过期后**返回旧值
并把刷新丢给后台线程**（每租户同时最多一个在飞），冷启动则先返回 0 再补。
"滞后 3 秒"和"滞后 3 秒零一个 RTT"语义上没区别，延迟上差一个数量级。需要
确定性读的地方（后台任务、测试）用 `refresh_now()`，它是显式阻塞的那一个。

**顺带治了弃权结果的 TTL。** 上面那条链路里，真正让人恼火的不是缓存本身，
是"我不知道"和"我知道"享受同样的 15 分钟。弃权的含义是"以现在的语料回答不了"
——而一个人紧接着重问同一句的最常见原因，恰恰是他刚把缺的那份文档补上。现在
弃权结果走 `abstain_ttl_s`（默认 60 秒，`RAG4C_QUERY_CACHE_ABSTAIN_TTL_S`
可调），L1 / L2 / L2 回填三处都按这个口径。策略写在
`QueryCache._ttl_for()` 里而不是交给调用方：写缓存的入口有三处，逐个叮嘱
"记得给弃权传短 TTL"迟早会漏。判定要认 `{"result": {...}}` 这层信封——
`server.app._serialize` 把 `abstained` 包在里面，只看顶层的话这个策略会静默
失效，测不出来也不报错。

代次与短 TTL 是互补的：代次覆盖走完整入库流程的情况，短 TTL 兜住代次不会涨
的那些（外部直接写 Milvus、上一次弃权只是因为重排抖了一下）。

回归：`scripts/smoke_cache_epoch.py`（30 条断言，含跨实例可见性、降级沿用旧
值、冷启动不阻塞、L2 上弃权键的真实 PTTL）。

### ⑯ 每问一次就重新算一次查询向量

同一个问题反复出现是问答系统的常态（热点问题、前端重试、多副本轮询），但
`embed_query` 每次都老老实实打一趟嵌入服务。实测这一步约 1.3s，而
`embed(model, text)` 是个**纯函数**——同样的模型、同样的文本，向量必然相同。

`core/embed_cache.py`：L1 进程内 LRU（512 条）+ L2 Redis（TTL 24h）。

几个决定值得写下来：

- **键里必须有模型名和变体**，不能只有文本。换了嵌入模型而键不变的话，
  拿到的是上一个模型的向量——检索不会报错，只会悄悄召回一堆不相干的东西。
  用 `\x00` 分隔而不是直接拼接：`("m1","ab")` 和 `("m1a","b")` 拼出来是同一
  个串。
- **不需要语料代次。** 这和答案缓存不一样：答案缓存缓的是整条链路的产物，
  输入含检索结果，语料变了就该失效；这一层缓的是 `文本 -> 向量`，语料变不
  变都不影响这个映射。
- **只缓 `embed_query`，不缓 `embed_texts`。** 入库是一次性的批量行为，缓
  下来几乎不会再命中，却会把共用的 Redis 撑爆。
- **float32 小端打包**（`struct.pack("<{n}f")`）而不是 `array.tobytes()`：
  后者是本机字节序，跨架构副本读出来是一堆垃圾数；float64 则白白多占一倍。

回归：`scripts/smoke_embed_cache.py`（30 条断言）。

### ⑰ 检索期的 LLM 调用没有任何缓存

改写、路由、HyDE、子查询、退一步这些「预处理」槽位每次都真调 LLM。它们和
生成不同：**prompt 里不含检索结果**，所以「同样的请求 -> 同样的输出」成立，
可以直接按请求摘要缓存。

`core/llm_cache.py` + `core/llm.py` 的 `_cache_lookup` / `_cache_store`。

- **开关做在槽位配置上**（`LlmSlotSettings.cache_ttl_s`，`0` = 不缓），而不是
  在 14 个调用点上各传一个参数。缓多久是槽位的不变量，不是每次调用的决定。
- **只有六个检索期槽位默认开**（1800s）。`generation` 明确排除：它的 prompt
  里带着检索结果，而 ACL 决定了能检索到什么——**prompt 相同不代表看得见它
  的人相同**，那一层必须由 `core/query_cache.py` 按租户 + ACL + 代次去缓。
  `judge` 排除是因为证据块巨大且几乎只在答案缓存本就会命中时才命中；入库
  三件套排除是因为按块计量会把共用 Redis 撑爆。
- **键里不放槽位名。** 两个槽位若拼出完全相同的请求，那问的就是同一件事。
- **值是个信封** `{"t": 文本, "p": prompt_tokens, "c": completion_tokens}`
  而不是裸文本。多存两个整数，是为了让「缓存省了多少 token」变成**实测**：
  命中时把当初真实花掉的用量原样报进 `llm.cache.saved.*`，和 `llm.tokens.*`
  是同一把尺子。否则只能拿「命中次数 × 拍脑袋的平均值」去估——那不是测量。
- **`chat_json` 传了校验器**（`cache_ok`）。这条路径上「模型返回的不是合法
  JSON」是常态，而 JSON 槽位恰好默认开着缓存。不校验的话，一次偶发的坏输出
  会被黏住整个 TTL：之后每个请求先吃一发命中的坏值、再真调一次修复，稳定地
  花双份钱。缓存里已有的坏值在读到时就地作废。

#### 差点又是一次「功能齐备、接线断开」

`cache_ttl_s` 最初写成容器上的字段默认值：

```python
rewrite: LlmSlotSettings = LlmSlotSettings(temperature=0.2, cache_ttl_s=1800.0)
```

这**看起来**是对的，单元测试也全绿。但 pydantic 的字段默认值是**整个嵌套
对象**的默认值：只要配置里出现了 `llm.rewrite`（哪怕只写了一个 model），
pydantic 就拿那份配置重新构造一个 `LlmSlotSettings`，`cache_ttl_s` 随之落回
类级默认的 `0.0`。而本项目的 `.env` 恰好给六个槽位都配了 model——

打印真实配置，六个槽位**全是 0.0**：缓存代码一行都不会执行，不报错，命中率
恒为 0。这和 ⑬ 之前「SSE 缓存接好了但命中率恒为 0」是同一类故障。

修法是把它变成校验器里的不变量而不是字段默认值（`config/settings.py` 的
`_default_cache_ttl`，挂在 `_apply_provider_refs` 上，和 `_inherit_conn` 一
样在每条构造路径上都跑）。用 `model_fields_set` 判断有没有显式写过而不是
判 0——否则「我就是要把这个槽位关掉」没法表达。

**教训是关于测试的：**原来的断言写的是 `LlmSlotsSettings()`（裸容器），
所以它证明了「配置里什么都不写时是对的」，而生产恰恰不是那样。现在的断言
建在**被覆盖过的**容器上，并且直接读 `.env` 断言真实配置。用 mutation 验证
过：把修复摘掉，9 条断言变红。

回归：`scripts/smoke_llm_cache.py`（48 条断言）。

### ⑱ TTL 一模一样，于是集体过期

`core/query_cache.py` 早就有 TTL 抖动，但抽出 `core/two_level_cache.py` 骨架
时，向量缓存和槽位缓存写的是精确 TTL。

这一层的同步过期尤其明显：一次查询会在**同一瞬间**把改写、路由等槽位的结果
一起写进去，它们带着一模一样的 TTL，于是也在同一秒集体过期——下一个同样的
问题不是少命中一条，而是整套预处理全部落空。批量预热、重启后的第一波流量
同理，只是规模更大：缓存把负载从「平摊」整形成了「周期性尖峰」，尖峰高度
恰好等于命中率。

抖动**只往短里抖**：两个方向的代价不对称，提前过期最多让某个值多算一次，
延后过期是多发一次陈旧内容。这也让所有「TTL 是上界」的断言继续成立。

实现下沉到 `two_level_cache.jittered_ttl`，`QueryCache._jittered` 改为调它。
共用一份是因为抖动幅度是个会被反复调的旋钮，两份拷贝迟早会调歪一份，而歪掉
的那份不会报错，只会在某个整点上突然多打一批 LLM 调用。

### 缓存这一层还剩多少空间：实测

上面三项做完之后，对着真实上游（DashScope + Milvus 8369 块 + 硅基流动）跑了
一次单问题的分阶段计时，结果值得记下来，因为它**否定了**下一步的直觉方向：

| 阶段 | 副本 A（冷） | 副本 B（改写命中缓存） |
|---|---|---|
| `query.total` | 61.6s | 45.4s |
| `span.verify_l3` | **30.9s** | **17.8s** |
| `span.generate` | 15.5s | 14.9s |
| `span.gate`（含改写的 LLM 调用） | 7.4s | 3.8s |
| `span.search` | 2.8s | 4.6s |
| `span.rerank` | 1.2s | 1.2s |
| `span.embed` | 1.3s | — |
| 真实 LLM 调用次数 | 3 | **2** |

槽位缓存确实生效了（`llm.calls` 3 -> 2，`llm.cache.saved.total` = 939 token）。
但**检索 + 重排 + 嵌入加起来只占约 8%**，而裁判（`verify_l3`）一家就吃掉
45%~50%。也就是说：

> 再往下堆缓存层（检索结果缓存、语义缓存）能拿到的收益，比裁判阶段的一个
> 配置改动小一个数量级。裁判用的是和生成同一个 `qwen3.7-max`，prompt 约
> 6900 token——换个更快的模型、或让它和生成并行，都不是缓存问题。

所以 P1-2（检索结果缓存）和 P1-1（语义缓存）**降级为后续可选项**，
瓶颈转交 §4。样本只有 2 次（每次要花真实 token），方向清楚但数值不精确。



按影响排序，留给后续：

- **裁判阶段（`verify_l3`）占端到端延迟的 45%~50%**（实测 17.8s / 30.9s，
  见上一节的表）。它用的是和生成同一个 `qwen3.7-max`，prompt 约 6900 token。
  这是目前最大的单点开销，而且**不是缓存能解决的**——缓存那一层的空间已经
  基本用尽。三个方向，成本从低到高：给 `judge` 槽位换个更快更便宜的模型
  （纯配置改动）；让裁判与生成并行而不是串在后面；把 L3 裁判降级为抽样或
  异步（答案先出，判定后补）
- 嵌入 / 改写 / 路由 LLM / 裁判仍无熔断（检索、生成、重排已覆盖）
- 第二轮检索（`rag.py:417-422`）收益近乎为零
- `verify/verifier.py:331-332` 重复嵌入 Milvus 里已有向量的证据文本
- `/api/eval/run` 用了第三个 executor（`run_in_executor(None, ...)`）
- `indexing/parsers/mineru_http.py` 的 `_ensure_session` 有同样的 Session 共享
  问题，但入库路径逐文件串行，并发度远低于问答路径，暂不改
- ~~指标 / 缓存 / 熔断状态都是单进程内存态，挡住横向扩容~~ —— 答案缓存与
  准入队列已跨副本（见 ⑬⑭）；**指标与熔断状态仍是单进程内存态**：每个副本
  各自计数、各自熔断，监控面板看到的是局部视图，熔断也不会在副本间传播
- 无按 IP / 租户限流
- 优雅停机 `wait=True` 最坏可能等 240s+
- **四个检索增强功能配了但没在跑**（做 ⑰ 时顺带查出来的，因为要确认槽位缓存
  到底会被哪些调用点用到）：`hyde_on` / `subqueries_on` / `stepback_on` 三个
  开关默认 `False` 且 `.env` 没开，`rag._build_optional_components` 连对象都
  不会构造；`catalog.auto_filter_on` 同样默认关，而且更严重——
  `retrieval/auto_filter.py` 的 `create_auto_filter` **零调用方**，
  `retrieval/pipeline.py` 里根本没有 `auto_filter` 参数，
  `auto_filter.py` 开头那句「组件由 rag.get_pipeline 注入检索管线」是**假的，
  这条线从来没接上过**。也就是说 `metadata_filter` 槽位目前是死代码。
  结论：一次普通提问真正会走到的检索期 LLM 槽位**只有 `rewrite` 一个**
  （`router_llm` 要同时满足改写有变化 + 嵌入路由置信度差 < 0.1，不确定）。
  要么把这几个开关打开并把 auto_filter 接上，要么删掉——现在这样最费解

## 5. 前端验收顺带查出的两个后端缺陷

截图验收时文档管理页上挂着一条鲜红的失败记录，顺藤摸下去是两个真问题。

### 纯文本直读被 parser 挡住

`.md` 入库失败，报「解析器不支持该文件类型」。根因在 `indexing/ingest.py`：
纯文本直读原先只在 `self.parser is None` 时可达。一旦为 PDF 配上 MinerU，
`router.supports('.md')` 返回 False，于是**最普通的 markdown 反而入不了库**——
错误文案还把「这个 parser 管不了」说成了「系统读不了」。

改为把直读当**兜底**而非"没配 parser 时的特例"：parser 不认的后缀，只要在
`_PLAINTEXT_EXTENSIONS` 里就直读。真不支持时的报错也补上了是哪个 parser 拒的。

测试为什么没拦住：`smoke_indexing.py` 只覆盖了"没配 parser"这一条，正好绕开
了出问题的分支。已补 (7b) 覆盖"配了 parser 但它不认这个后缀"。

### 异常文本原样显示给用户

页面上那条失败信息长这样：

    解析器不支持该文件类型: 'D:\\program_project\\python_project\\RAG4C\\data\\test_kb.md'（doc_id='doc-efeaae642df9'）

双反斜杠是 `{path!r}` 的转义，用户看着像乱码；绝对路径把服务端目录结构摊给了
所有能打开这个页面的人；doc_id 在表格里本来就有独立一列。

新增 `catalog.sanitize_error_message()`，在 `set_document_status` 这**一个写入口**
统一处理——而不是让三处 `str(exc)` 的调用方各自记得先清洗。原始异常仍完整落
在日志里，排查不受影响，收拾的只是展示。

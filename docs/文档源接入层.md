# 文档源接入层（`sources/`）

把「某个地方的一堆文档」变成「知识库里可检索的内容」，并且**可增量重跑**。

目标是让新增一个文档来源不需要改代码主干：官方文档仓库、内网目录、
将来的 Context7 / S3 / Confluence，都走同一条路。

---

## 快速上手

```bash
# 看有哪些源类型、清单里配了什么
python scripts/ingest_source.py --list

# 空跑：只抓取比对，不写库（先确认路径没抓错）
python scripts/ingest_source.py --source milvus --dry-run --limit 5

# 真入库
python scripts/ingest_source.py --source milvus
python scripts/ingest_source.py --all

# 校验：文档在不在库、能不能召回、知识库隔不隔离（不调 LLM，秒级）
python scripts/verify_docs_kb.py

# 最后一段：真的让模型基于官方文档作答（调 LLM，实测单问 30~90 秒）
python scripts/ask_docs_kb.py
```

同步完之后，知识库对 HTTP 客户端是**可发现的**：

```bash
curl localhost:8000/api/datasets
# {"datasets":[{"dataset_id":"springboot","origin":"source","doc_count":177,
#               "chunk_count":1729,...}, ...],"count":6}

# 拿到 dataset_id 就能限定检索范围
curl -X POST localhost:8000/api/query \
     -d '{"query":"What is a Spring Boot starter?","dataset_id":"springboot"}'
```

`/api/datasets` 合并两个来源，因为知识库有两种进库方式、各自只知道自己那半边：
`origin="source"`（`config/sources.json` 声明、由源同步写入）与 `origin="catalog"`
（业务上传路径写入，带描述与租户归属）。`chunk_count` 一律现查 Milvus——它才是
「检索时真的能命中多少内容」的唯一事实，任何一边的记账都可能漂。Milvus 不可达时
该字段为 `null` 而不是 `0`：`0` 会被读成「这个库是空的」，和「暂时数不出来」
是完全不同的结论。

## 三层结构

| 模块 | 职责 |
|---|---|
| `sources/base.py` | 契约：`DocumentSource` / `FetchedDocument` |
| `sources/registry.py` | 插件注册表：按名字创建源实例 |
| `sources/github_repo.py`、`sources/local_dir.py` | 两个内置源 |
| `sources/plugins.py` | 内置源注册（import `sources` 即生效） |
| `sources/runner.py` | 执行器：清单解析、增量判定、批量入库、删除清理 |

配置在 `config/sources.json`（示例见 `config/sources.example.json`），
路径由 `settings.sources.manifest_path` 决定。

---

## 几个刻意的设计选择

### 源的产物是**本地文件路径**，不是内存里的文本

`FetchedDocument.local_path` 指向一个真实文件，入库走 `pipeline.add_file()`。

如果产出字符串走 `add_document()`，就会绕过 cleaner、预切分策略和切分模式
路由——同一篇文档「本地导入」和「远程同步」会切出不同结果。落盘还带来两个
附带好处：抓到的东西可以直接打开检查；重跑时本地缓存能直接复用。

### 源清单是独立 JSON，不是 `.env`

源的参数是结构化的（`include` 是数组、`params` 是嵌套对象），`.env` 只能
表达扁平字符串；而且 `config.settings.Rag4cEnvSource` 明确跳过 dict 字段，
本来也映射不进来。独立文件还能进版本库，改了什么一目了然。

### 注册表形态照抄解析器，但**选择语义相反**

`indexing/parsers/registry.py` 是「从若干候选里挑一个用」，所以有 priority
和 auto。文档源是「同时接入多个、各带各的参数」——SpringBoot 文档和 Milvus
文档是并存关系而不是备选关系。所以这里没有 priority、没有 auto。

沿用同一套形态的好处仍在：**新增一种源 = 一个类 + 一行注册**，注册表和
调用方零改动。

### `dataset_id` 默认等于源名

一个源天然对应一个知识库，让「每个项目的文档各自成库」成为不需要额外配置
的默认行为。需要几个源共用一个库时再显式写 `dataset_id`。

注意 `dataset_id` 和 `tenant_id` 不是一回事：tenant 是**安全边界**
（enforced 时空值强制回退到默认租户），dataset 是**检索范围**（空即全域，
不做强制）。

## 增量是这一层的核心价值

官方文档仓库动辄上千篇，全量重跑要把所有内容重新嵌入一遍，既慢又白花
嵌入调用。状态文件（`<cache_dir>/<source>/_state.json`）按内容哈希做文件级
跳过，只有真变了的文档才重新解析 + 嵌入 + 写库。

几条容易写错、已在 `scripts/smoke_sources.py` 里钉死的规则：

- **`doc_id` 必须只由 (源名, 相对路径) 决定。** 不稳定的话旧 chunk 永远删不掉，
  库里会不断堆积同一篇文档的历史副本。
- **内容变了要先删旧 chunk 再写新的。** 不删的话新旧两版同时在库里，检索可能
  召回早已被改掉的说法——比检索不到更糟。
- **上游删掉的文档要从库里清掉**，否则知识库残留早已不存在的内容。
- **`--limit` 截断时绝不能做删除。** 那种情况下「本轮没出现」只说明还没轮到，
  照删会把好好的文档整片抹掉。未处理到的旧状态条目要原样留下。
- **单篇失败不写进状态**，下次运行会重试；写进去会让一次偶发失败变成永久跳过。

## GitHub 源的两条抓取路径

| 模式 | 做法 | 适用 |
|---|---|---|
| `tarball` | codeload 一次请求拿仓库快照，流式解包边下边筛 | 文档占仓库大头 |
| `api` | trees API 拿清单，再从 raw 逐个下载命中的文件 | 大仓库里只要一小片 |
| `auto`（默认） | 用 trees API 里的 blob 尺寸算「要的字节/全仓字节」，按比例择优 | 一般都用这个 |

为什么两条都要：`redis/docs` 有一万多个文件、`spring-boot` 有一万一千多个，
而我们各自只要两百来篇。为这点内容拖整个快照，在慢网络上要多花十几分钟；
反过来 `milvus-docs` 全仓才 152 个文件，逐个请求的往返开销反而更亏。

`api` 路径顺带拿到一个便宜的好处：trees API 返回的 blob sha 本身就是内容
哈希，本地缓存文件若算出同一个 sha，连下载都省了。

**已知网络问题**：部分网络能连 `codeload.github.com` 和 `api.github.com`，
却会重置到 `raw.githubusercontent.com` 的连接。`auto` 模式下这会自动回退
到 tarball（仅在尚未产出任何文档时回退，避免同一批文档产出两次）；显式指定
`mode: "api"` 则照常报错，不替使用者改主意。

## 新增一种源

```python
# sources/my_source.py
class MySource(DocumentSource):
    name = "my_source"

    def describe(self) -> str:
        return "一句话说明"

    def fetch(self, workdir: Path) -> Iterator[FetchedDocument]:
        ...  # 落盘后 yield FetchedDocument(uri, rel_path, local_path, content_hash)
```

```python
# sources/plugins.py 的 register_builtin_sources() 里加一行
register_source_plugin(SourcePlugin(
    name="my_source",
    factory=lambda params, settings: MySource(**params),
    describe=lambda: MySource.__doc__.strip().splitlines()[0],
    required_params=("some_required_param",),
))
```

然后在 `config/sources.json` 里用 `"type": "my_source"` 声明即可，
runner、CLI、增量、删除检测全部自动适用。

## 两个校验脚本的分工

| 脚本 | 验到哪一层 | 代价 | 什么时候跑 |
|---|---|---|---|
| `verify_docs_kb.py` | 入库统计、领域内召回、知识库隔离、BM25 是否真的在起作用 | 不调 LLM，秒级 | 每次改完检索链路 |
| `ask_docs_kb.py` | 再往前一步：生成 + 引用验证 | 云端 LLM 单问 30~90 秒；本机 CPU 240~1140 秒 | 大改之后确认一次 |

分开是刻意的。把生成塞进快脚本，它就会因为太慢而没人跑；两个都做成慢的，
改检索时就失去了秒级反馈。也因此 `ask_docs_kb.py` **不进** `run_tests.py`——
21 个冒烟脚本现在总耗时 40 秒，加一个上千秒的进去，整套就不再有人愿意跑。

`ask_docs_kb.py` 的判据不是「答案看起来对」（那要人读），而是两条机器可判的
硬条件：库里明明有对应官方文档却弃权，说明链路某一环没接上；有答案但零引用，
说明答案无法溯源——那就等于没有 RAG。

### 已知问题（已解决）：过度弃权的根因是判定模型，不是阈值

曾经实测三问：springboot（英）与 milvus（中）都给出了有据可依的答案，但
langgraph 那问**弃权了**——而它的检索毫无问题，重排后 top1 得分 0.978，
命中的正是 `checkpointers.mdx` 本身。也就是说卡点不在检索，在弃权门的第二道：
生成完之后的蕴含/引用验证分数没到 `pipeline.entailment_score_threshold`（0.6）。

当时摆着两条解法：把槽位指向云端，或者调低阈值。**结论是前者**——把
generation / judge 指向通义千问后，同一问从「1140 秒、弃权、0 引用」变成
「39 秒、16 条引用且全部 `ok`」。阈值一动没动。

这个结果值得记一笔：`entailment_score_threshold` 是「答案必须有据可依」这条
底线的数值形式，调低它能立刻让弃权变少，但换来的是把幻觉放行。当验证分数
偏低时，**先怀疑判定模型的能力，再怀疑阈值**——本机 CPU 上的 qwen2.5 既是
耗时大头，也是验证质量的短板，两个症状同源。

| | 本机 Ollama（qwen2.5, CPU） | 通义千问（qwen3.7-max） |
|---|---|---|
| springboot | 239s，14 引用 | 90s，11 引用 |
| milvus | 通过 | 31s，7 引用 |
| langgraph | **1140s，弃权，0 引用** | **39s，16 引用** |

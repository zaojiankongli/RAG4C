## 3. 循环与任务约定

**产品主线（CONTEXT.md）**  
RAG4C KnowledgeOps 的定义体验是 **Knowledge Lifeline**：答案可从 citation → retrieval → index projection → chunk revision → document version → parser run → source identity 逐级回溯。

**compose-next 节奏（每 tick）**

1. 先收尾未完成切片；否则按候选优先级选一薄片。
2. 写/更新 `docs/compose/spec/<feature>.md`（蓝图书：范围、Tasks、覆盖映射）。
3. 实现 → **live** 门禁（目标 pytest + tsc + 定向 vitest）→ 独立 review agent。
4. Finalize spec：`status: delivered`，`commits: <base>..<sha>`，Report 写清 What/Verification/Journey。
5. Commit 到 `integration/qa-faq-ops`；FF：`git fetch . integration/qa-faq-ops:main` 与 `:feature/knowledgeops-authority`。
6. 回报：切片名 / SHA / 门禁读数 / 下一候选。**不 push。**

**用户偏好**

- 语言：回复默认 **zh-CN**。
- 「继续 / 别停」= 直接开工，不要长 grill。
- 需要选择时用 `question` 工具，**推荐选项放第一且标 (Recommended)**。
- 成功标准：证据驱动（只写**本轮**新跑的测试结果）；spec 落在 `docs/compose/spec/`；commit 在 integration；merge tips 保持对齐。
- **不要**自动 finish/push/删分支，除非用户明确要求。
- **不要**在未验证情况下叠多个大切片（除非用户说「全部都做」）。

**Cron prompt 要点（job `350d6004`）**  
先未完成切片 → 否则 WeKnora/CONTEXT/console 缺口；门禁 = 定向 pytest + tsc/vitest；报告切片/SHA/门禁/next。

## 7. 域不变量与产品语言（不可破）

摘自 `CONTEXT.md`，评审时逐条对照：

1. 手工改 chunk 必须先产生不可变 revision，再改 head。

- Run History：运维证据，≠ 知识真源。

## 10. 独立评审如何「接受」交付

评审智能体（或后续 loop 的 review 步骤）应：

1. **读 tip**：`git rev-parse --short HEAD`，与 spec `commits` / 本文件对照。  
2. **live 读代码**：按 §5 抽查生产 wiring 是否存在且被调用。  
3. **live 跑门禁**：§6 定向命令；禁止只粘贴历史 PASS。  
4. **对照不变量**：§7 + CONTEXT.md。  
5. **对照产品语言**：字段帮助、UI label、领域词。  
6. **输出签收块**（§1 格式）写进 ReviewTrace / 下一 agent 的 report。  
7. **FAIL 时**：写清 blocker 文件:行、期望 vs 实际、建议修复方向；不要「综合通过」。

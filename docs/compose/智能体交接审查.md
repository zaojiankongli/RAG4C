## 3. 循环与任务约定

**产品主线（CONTEXT.md）**  
RAG4C KnowledgeOps 的定义体验是 **Knowledge Lifeline**：答案可从 citation → retrieval → index projection → chunk revision → document version → parser run → source identity 逐级回溯。

**compose-next 节奏（每 tick）**

1. 先收尾未完成切片；否则按候选优先级选一薄片。
2. 写/更新 `docs/compose/spec/<feature>.md`（蓝图书：范围、Tasks、覆盖映射）。
3. 实现 → **live** 门禁（目标 pytest + tsc + 定向 vitest）→ 独立 review agent。
4. Finalize spec：`status: delivered`，`commits: <base>..<sha>`，Report 写清 What/Verification/Journey。
5. Commit 到 `integration/qa-faq-ops`；FF：`git fetch . integration/qa-faq-ops:main` 与 `:feature/knowledgeops-authority`。
6. 回报：切片名 / SHA / 门禁读数 / 下一候选。**不 push。**

**用户偏好**

- 语言：回复默认 **zh-CN**。
- 「继续 / 别停」= 直接开工，不要长 grill。
- 需要选择时用 `question` 工具，**推荐选项放第一且标 (Recommended)**。
- 成功标准：证据驱动（只写**本轮**新跑的测试结果）；spec 落在 `docs/compose/spec/`；commit 在 integration；merge tips 保持对齐。
- **不要**自动 finish/push/删分支，除非用户明确要求。
- **不要**在未验证情况下叠多个大切片（除非用户说「全部都做」）。

**Cron prompt 要点（job `350d6004`）**  
先未完成切片 → 否则 WeKnora/CONTEXT/console 缺口；门禁 = 定向 pytest + tsc/vitest；报告切片/SHA/门禁/next。

## 7. 域不变量与产品语言（不可破）

摘自 `CONTEXT.md`，评审时逐条对照：

1. 手工改 chunk 必须先产生不可变 revision，再改 head。
2. Projection 写入必须 revision fenced。
3. 删除是 durable operation，不是同步 best-effort 多存储事务。
4. 生产失败必须可见；demo 数据仅在显式 demo mode。
5. 所有变更型操作员动作必须 tenant scoped + audited。
6. 知识过期：禁检索但保留数据，直至显式 retention 删除。
7. 自动 QA 生成必须 review 后才可进检索。

**单一真源**

- MySQL Catalog：identity / lifecycle / versions / operations / audit / permissions。
- Milvus：搜索投影，**无业务真源**。
- Graph：图投影，**无业务真源**。
- Redis：有界瞬时态。
- Run History：运维证据，≠ 知识真源。

**领域词（文案与文档）**  
Knowledge Base、Knowledge Lifeline、Document Identity/Version、Chunk Head/Revision、Projection / Projection Fence、Index Operation、Knowledge Source、Ingest Attempt、Knowledge Folder/Tag、QA Knowledge、Evidence Chain、Consistency Console。

QA 配置文案示例（应保持同调）：`server/app.py` FIELD_HELP 中「QA 权威检索」「Catalog 中已审核且启用检索的 FAQ 并入证据（不投影 Milvus）」。

   在 `graph_index_on` 下重新入库并做多跳问答观测（历史审查缺口）。  
   验收：有证据链的 multi-hop 样例 + 失败可见。

5. **active 模式 `chunk_count` 与 enabled-head 计数漂移（已实测并修掉，`bc00a46`）**  
   评审以"未证实推论"形式提出：active 分支下 tombstone 不调 `_update_document_after_delete`，
   `doc.chunk_count` 会落后于 enabled-head 真实数量，而 active 的完整性栅栏正是比对这两个数。
   我用一次性脚本实测为真，且后果比描述更重：删掉一个切片后，该文档**所有**后续切片写
   （含未触及的切片、含本轮新上的 restore/revert）全部被判"权威不完整"而 409 —— 一次成功删除
   即可永久卡死整个文档的切片编辑。HEAD 亦如此，既有测试没暴露是因为它们不做"删后再写"。
   处置：tombstone 在 active 下也落计数与人工删除审计（计数取权威值），restore/revert 改变
   enabled 集合后按权威重算写回，一致时不多写 UPDATE。回归见 `tests/test_chunk_count_reconciliation.py`。

6. **切片逐版修改原因（Alembic 0040）** —— 本轮按裁定把原因落在 `chunk_heads.chunk_metadata`，
   代价是 `chunk_revisions` 无逐版原因。升级需同步 `HEAD_REVISION`、capability 白名单、
   `_REVISION_ORDER_FOR_CAPABILITY` 与 `tests/head_catalog.py` 时代夹具声明（R7 §5.2 实测会带来约 20 条漂移）。

7. **restore/revert 的服务层集成测试** —— 现有覆盖是：`_durable_operation` 真值表（单元）、
   生命周期端点契约（HTTP 层，含跨租户 404）、catalog 层 reason 落库。**缺**真
   `IndexOperationQueue` 下"墓碑→恢复"确实重新入队 upsert 投影 的服务层用例；
   脚手架可复用 `tests/test_chunk_authority_api.py` 的 `FakeCatalog`/`queue`/`ledger`。

8. **可选清理（用户侧）**  
   `git branch -d salvage/qa-faq-ops-wip`；`.worktrees/` 保持 untracked 或本地清理。

**选股标准**：能缩小 Catalog↔投影↔证据 的漂移，或降低运营发现/调参成本；薄片优先；必须有可测证据。

## 10. 独立评审如何「接受」交付

评审智能体（或后续 loop 的 review 步骤）应：

1. **读 tip**：`git rev-parse --short HEAD`，与 spec `commits` / 本文件对照。  
2. **live 读代码**：按 §5 抽查生产 wiring 是否存在且被调用。  
3. **live 跑门禁**：§6 定向命令；禁止只粘贴历史 PASS。  
4. **对照不变量**：§7 + CONTEXT.md。  
5. **对照产品语言**：字段帮助、UI label、领域词。  
6. **输出签收块**（§1 格式）写进 ReviewTrace / 下一 agent 的 report。  
7. **FAIL 时**：写清 blocker 文件:行、期望 vs 实际、建议修复方向；不要「综合通过」。

实现 agent 在 self-review 时同样应用 A1–A10，**先修再 finalize**，避免依赖下游 review 补锅。

## 11. 明确不要做的事

- 不要 push 到远端；不要 force；不要删分支（除用户明确指令且绕过沙箱限制）。
- 不要在测试失败、门禁未跑、spec 未 finalize 时把 `status` 写成 `delivered`。
- 不要把 Milvus / Graph / Redis 当业务真源写回 Catalog 语义。
- 不要引入 demo 数据掩盖生产失败。
- 不要让 pending/rejected QA 进入检索。
- 不要忽略 catalog soft-fail 的日志/metrics。
- 不要在一个 PR/tick 里堆未验证的大切片。
- 不要把 `.worktrees/` 或 salvage 调试文件提交进 integration。
